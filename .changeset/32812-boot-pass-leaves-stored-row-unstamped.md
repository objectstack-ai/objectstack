fix(metadata)!: the boot priming pass leaves a package-less stored row of a type stored per `(package, name)` unstamped, so the host's package is never counted as a holder of its name (ADR-0150 D4)

Clause-②: yes (narrowing) — one face widens against the last release and the others narrow, all on a host that declares its package and wires a `DatabaseLoader`; the widening is named under the BREAKING banner below. Narrows: on a host that declares its package (`MetadataPlugin`'s `packageId`) and wires a `DatabaseLoader`, a package-less `sys_metadata` row of `api`, `agent`, `skill`, `action`, `email_template`, `permission`, `flow`, `picklist`, `mapping` or `dataset` is no longer served as the host package's item after the boot priming pass: its body no longer carries `_packageId` set to the host's package or `_provenance: 'package'`, the metadata list filtered by the host's package (`?package=` naming it) no longer lists it, and `publishPackage`, `revertPackage` and `unregisterPackage` naming the host's package no longer take it as one of that package's items. The `409` this lifts (the bare read naming the host's package, which holds nothing, after a write that carries no package) is #32560's, which has not shipped.
Metadata-protocol: none — no key, value or metadata type an author writes changes; what moves is which package the boot pass gives a stored row that names none.

**BREAKING** for a host that declares its package and stores rows that name no package for one of these ten types. Such a row is the environment's own item, or the customization of the one package that holds its name (ADR-0150 D4); it was never the host package's, but the boot pass stamped it so. To keep an item in the host's package, save it naming that package (`?package=` on the write, or the package stamped on the item `register` is given). A row whose stored body an earlier release's boot pass wrote the host's stamp into is still read as the host package's (its column is bound from that body), and is not moved. Every other type, and the host's own file items, are stamped as before.

The one widening, a behaviour change for the same reason (ADR-0150 D4, and the answer a host that declares no package already gives): a package-less stored row of these types is no longer hidden when the host's own package is disabled, as on a host that declares no package.

What reads the stamp moves with it: such a row with a `protection` block is locked from `'artifact'` rather than `'package'` (`_lock` kept), an MCP skill or agent face built from it is named by its own name rather than the host's namespace, and the realtime events of the boot pass carry no package for it. No first-party package, app or example declares a package and wires a `DatabaseLoader`.

Moved answers, all on such a host, each now the answer the same composition gives on a host that declares no package:

- One package's row and a package-less row saved last (`action`): after `register` with no package, or `registerInMemory` of a package-less item, the bare `get` and `getDiagnosed` go from `409 RESOURCE_CONFLICT` naming the host's package, the holder and the environment to the written item.
- The removal naming no package, the same composition: right after the pass and after such a write, it goes from a `409` naming the host's package to removing the package-less row, for every one of the ten types (`email_template`: the holder's slot), so it names the holders the bare read names.
- The same composition, the nine unbundled types: the registry holds the package-less row in the name's bare slot, not the host's, and a read naming the holder answers its customization (the package-less row) where it answered the holder's own row. `list` names the row once, package-less, where it named it twice (its customization and, again, the host's), so a consumer that counts the holders `list` names counts one holder where it counted two.
- A read naming a package that holds nothing (the host's own, on a host declaring the holder's package; any third package, on a host declaring another): it answers the package-less row (or the item written over it), as the bare read does, where it answered nothing. The other way, the read naming the host's package goes from the package-less row to nothing where a package's item registered in memory sits beside that row, and for `email_template` beside one package's row: the host's package holds nothing there.
- A package-less row and one package's `action` item registered in memory after the pass: the bare read answers that package's item, where it answered the package-less row (the by-host difference #32752 tracked).
- The package-less row deleted from the table behind the manager: the bare read answers the registry's copy, where it was refused naming the host's package and the holder.
- `email_template`, one package's row and a package-less row: the pass files the package-less row in the holder's slot (its customization) and no longer in the host's, so the bare read after the pass is no longer refused naming the host's package.
- A package-less `action` row alone, removed with no package: the registry's stamped copy no longer outlives the row (it answered reads and `list` until a restart).

This replaces #32791's read-time filing of the stamped row (`MetadataManager`'s record of stored package-less rows, its overwrite mark and the judged view's filing), which has nothing left to file for the boot pass and is removed; every #32791 pin marked CONTROL passes unchanged. Of #32791's own changeset, which ships in the same release, three statements no longer hold: the filing it describes is gone, a read naming a package is no longer unchanged (above), and its "after the pass" cell (a package-less row, a package's item registered in memory after the pass) answers that package's item. One caller the filing also covered moves back: a caller of the public `MetadataManager.loadMany` that stamps a package-less row it is handed with a package itself and registers it is now refused naming that package beside the name's holder, as after any write (no first-party caller does so). Candidate order in a refusal is not promised.

Skills-docs: none — `skills/**` and `content/docs/**` do not teach that the boot pass gives a stored row the host's package; the migration step ships in this note and is carried into the release's upgrade notes when they are written.
