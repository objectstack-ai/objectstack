fix(metadata)!: the artifact door's in-memory loader and `DatabaseLoader` store `api`, `agent`, `skill` and `action` items per package, and a read that reaches them is answered by package

Clause-②: no (narrowing) — for a type in `PACKAGE_SLOTTED_STORE_TYPES` (today `api`, `agent`, `skill`, `action`), `MetadataManager.get`/`getDiagnosed` naming no package that reaches the loaders (no registry slot of the name) of a name two packages stored is refused `409 RESOURCE_CONFLICT` (`ambiguous-in-environment`, naming both) where it answered the body saved last; a read naming a package that stored nothing is not found where it answered another package's body; `unregister(type, name)` naming no package of a name two packages hold in the registry and the loaders together is refused the same way, before anything is touched; once every slot of a name is removed, the door's stored copy no longer answers.
Metadata-protocol: none

<!-- adr-0087: not-required (no-migration-prescription) no key of any schema is added, removed or re-shaped: what moves is which stored item a loader keeps and which one a runtime read is answered, and nothing an author writes needs converting -->

**BREAKING** only for a caller whose `get` of a by-package type reaches the loaders and relied on the body saved last.

ADR-0150 D3/D4 already stored these types per package in `MetadataManager`'s registry (#32069, #32151, #31697). The loaders under it did not: the artifact door's `MemoryLoader` and `DatabaseLoader` kept one entry per name, the body saved last, so the first package's stored item was gone at the second package's save; the manager's loader fallback named no package; `list` admitted loader items one per name; and a removal never deleted from the door's store.

- **The rule, once.** Both loaders hold these types by the rules in `package-slotted-store.ts`: the door's store under the registry's own keys (an object-bound action by its object and name, as the registry slots it), `DatabaseLoader` one row per `(package, name)`. A save fills the slot the store's write rule picks (a package-less body under a name one package holds is that holder's customization, D4), and a delete takes the slots `storeRemovalKeys` picks. The manager reads a by-package type that its registry cannot answer (no slot of the name, or a read naming a package where only other packages' slots are registered) over the registry's slots and every loader's stored items of the name (`MetadataLoader.loadSlots`, new and optional) through the same `readStoreEntry`, and judges a removal naming no package over the same holders; `list` and the endpoint index fill each package's slot from every item the loaders store (`MetadataLoader.loadManySlots`, new and optional).
- **The loaders' own reads, one item per name.** `load`, `loadMany` and `loadManyKeyed` on either loader — and so `MetadataManager.load`, `loadDiagnosed`, `loadMany` and `loadManyKeyed`, which read the loaders alone — still answer one item per name, the one saved last (for `DatabaseLoader`, the row changed last: an identical re-save writes nothing). The action router's third rung (`loadDiagnosed('action', …)`) and objectql's action audit (`loadManyKeyed('action')`) read what they read while the stored items stay; after a removal they no longer see the removed package's copy in the door's store (see the remedy).
- **Storage.** `DatabaseLoader` keeps one `sys_metadata` row per `(package, name)` with `package_id` filled. A row's package is that column, else the package its stored body names. Versions of these types are numbered per name, one past the highest the name has had over its packages' rows and its `sys_metadata_history` rows, so both packages' history rows are written (the table is unique on `(type, name, version)`) and a package removed and saved again never reuses a version; the row saved last is the name's highest version. A save binds the row it writes. For the rest, an operator runs `migrateDatabaseLoaderRowPackages(driver)` (`@objectstack/metadata/migrations`): it binds the loader's own rows (`source = 'database'`) whose body names a package, leaves a package-less row as it is, and can be re-run any number of times.
- **Removal.** `unregister` and `unregisterPackage` delete a by-package type from the in-memory loaders too (the artifact door's store), by the same key. `unregisterPackage(P)` also removes every item in P's slot, a package-less customization of P's item included. The realtime `created`/`updated` event names the package of an item that carries only the `_packageId` stamp, the way `deleted` already did.
- **Unchanged.** Every other type is stored, read and removed by name, as before (pinned as CONTROL), and its in-memory loader copy is still not deleted from (a separate card). A read the registry answers is unchanged.

**The remedy.** What a caller sees before and after, for a type in the set, with first-party reach:

- `get`/`getDiagnosed` naming no package that reaches the loaders, of a name two packages stored: FROM the body saved last TO `409 RESOURCE_CONFLICT` (`ambiguous-in-environment`), as the registry already answers it. Name the package in the read.
- `get`/`getDiagnosed` naming a package that stored nothing, where another package did: FROM that package's body TO not found.
- `get`/`getDiagnosed` naming a package, reaching the loaders: FROM the body saved last TO that package's own item.
- `get`/`getDiagnosed` naming a package whose item only a loader stores, where the registry holds another package's slot of the name: FROM not found TO that package's stored item.
- `unregister(type, name)` naming no package, of a name two packages hold in the registry and the loaders together (an empty registry over stored rows, a cluster peer after its replay): FROM resolving, deleting nothing (each loader's refusal logged as a failed delete), counted as succeeded by `bulkUnregister` and announced `deleted` (before this change: the name's row deleted whoever's body it held) TO `409 RESOURCE_CONFLICT` (`PackageScopedNameRefusedError`, `ambiguous-in-environment`) naming every holder, before anything is deleted or announced, and reported in `bulkUnregister`'s `errors`. Name the package, or use `unregisterPackage`. First-party callers today: 0; `permission` joining the set (#32162) brings plugin-security's bare `unregister` here.
- `list` over the loaders: FROM one item per name TO each package's item.
- the endpoint index (the `api` matcher's routes): FROM one loader-held `api` item per name TO each package's.
- First-party reach of these four: `DatabaseLoader` production wiring 0; cluster writers that notify on these types 0. The artifact door registers every item it stores, so on a door boot a read reaches the door's store only for a name no registry slot holds; the filesystem loader holds one package's items.
- after the last slot of a name is removed on an artifact-door boot: `list`, `get` and `exists` FROM the body saved last TO nothing; the loaders-only reads (`load`, `loadDiagnosed`, `loadMany`, `loadManyKeyed`) FROM the removed package's door copy TO nothing, or the other package's item while it is stored. First-party removal callers on these types: 0.
- `DatabaseLoader.save`: FROM one row per name with `package_id` empty TO one row per `(package, name)` with it filled; `delete` naming no package of a name two packages hold: FROM deleting the row TO refused.
- the realtime `created`/`updated` event of a `_packageId`-only item (any type): FROM no `packageId` TO the package; of an item whose `packageId` is empty or the `sys_metadata` provenance sentinel (any type): FROM that value TO no `packageId`. First-party `subscribeMetadata` callers: 0.
- `unregisterPackage(P)`: FROM leaving a package-less customization in P's slot TO removing it. First-party callers: 0.

**Recorded, not built.** A cluster peer's replay of a name-level change still drops every slot of the name; it now re-reads each package's item from the per-package storage, and only a slot no loader holds is lost, as for every type on `main` (per-slot invalidation was not ruled in). A removal on one node does not reach the peers' door stores: each peer's door copy of the removed package's item keeps answering there once the replay has dropped the slots. `unregisterPackage`'s membership (`packageId`, `package` or `_packageId` on the body) stays a second rule beside the slot rule, documented on `isPackageMember`. A package-less item beside two package slots keeps its own package-less row and is removable by name only once both packages are gone. `DatabaseLoader`'s rollback, `getHistoryRecord` and `queryHistory` stay keyed by `(type, name)`. For a name two packages hold, `registerRollback` writes the target version's body — whichever package saved that version — into the first row the driver returns for the name, keeping that row's `package_id`, so one package's body can land in the other package's row; rolling back one package's row is a follow-up card. One package's same-named actions bound to two objects share that package's row (the table's unique key has no object), the one saved last, as every name did before.
