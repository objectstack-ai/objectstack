feat(objectql): a nested-relation condition on a read verb is an in-database subquery per relationship, up to three relationships, each read-scoped on its own object, with no id cap; analytics serves the dataset's own `filter` the same way

Clause-②: yes (widening; narrowing on a related object another datasource holds, and on a driver that compiles no subquery) — widening: `{ account: { status: { $ne: 'cancelled' } } }` on `find`, `findOne`, `count` and `aggregate` (and so every analytics face that hands the engine the nested form) is served whatever the number of matching related records, where more than 1,000 answered `INVALID_FILTER` / 400. The related read is planned through its whole pipeline as the caller (CRUD gate, read middlewares including row scope and the filter-oracle guard on the condition's fields, `beforeFind` hooks, comparand doors) and its final `where` becomes the scope of a `ReadableIds` leaf the driver compiles into `field IN (SELECT id …)` with its tenant wall; a related record the caller cannot read is in no subquery, so it never matches, `$ne` included. A relation key inside the condition may now carry a condition of its own, down to ADR-0071's three relationships (`{ contact: { account: { region: { name: 'NA' } } } }`), where a second level answered `INVALID_FILTER` / 400: each hop is that object's own planned read, so each carries its read scope and field check, and a fourth relationship is refused by name. On the analytics engine-aggregate path a dotted `where` leaf through up to three relationships (`order.customer.tier`), and a cross-object leaf in a compiled dataset's own definition-level `filter`, reach the engine as that nested condition, where both answered `INVALID_FIELD` / 400; the SQL echo of such a dataset `filter` now refuses `INVALID_FILTER` / 400 (it printed no statement before either, refusing `INVALID_FIELD`). Narrowing: a single-valued condition on a related object bound to another datasource than the read's object now answers `INVALID_FILTER` / 400 naming both datasources, where the id read served it; on a driver that compiles no `ReadableIds` leaf (MongoDB, OData) the read is refused with that driver's ADR-0139 refusal, where the id read served it. A multi-valued relation and the `update` / `delete` verbs keep the id read and its cap; a per-measure `filter` carrying a cross-object leaf stays refused.
Metadata-protocol: none
Skills-docs: `content/docs/protocol/objectql/query-syntax.mdx` and `content/docs/kernel/contracts/data-engine.mdx` describe the subquery, the three-relationship limit, where the cap still applies and which drivers compile it. `skills/objectstack-query` still says "up to 1000 related ids" and one level for every relation; that is now stricter than the engine for a single-valued relation on a read verb (a follow-up skills-only change, governed).
