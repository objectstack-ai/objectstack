fix(cloud-connection, runtime, objectql): an install-local uninstall withdraws the package's action handlers and body hooks from the running engine, so a call that names no package is served by the one remaining holder at once instead of after a restart

Clause-②: yes (widening) — a bare `POST /api/v1/actions/OBJECT/NAME/ID` that answered `409 RESOURCE_CONFLICT` after an install-local uninstall, naming the uninstalled package as one of two owners, now answers with the one remaining holder's handler, its package's result in the reported case. `ObjectQL#removeActionsByPackage` also hands the key back on every other removal that empties the key a bare call reads while another owner still holds a handler under it in its own slot: the authored-action resync's teardown (`removeActionsByPackage('metadata-service')`, deleting an environment-authored action whose key host code or a plugin also holds), the binder's re-bind that drops a package body of a multi-package artifact, and `ObjectQL#removePackage`. In each, a bare call moves from "not found" to the one remaining holder's handler, and the unqualified `listRegisteredActions()` keeps listing the key, so the readers of that listing see the action again: MCP `list_actions`' handler probe (`registeredActionHandlerProbe`), the script door's owner check (`actionHandlerOwnerRefusal`) and the action-governance inventory. Every 409 the bare-call rule answers stays a 409. `@objectstack/runtime` gains the export `unbindAppArtifactHandlers` and the type `AppArtifactHandlerUnbinding`. All additive.
Metadata-protocol: none

**The defect.** `DELETE /api/v1/marketplace/install-local/:manifestId` withdrew the package from the registry and left every handler its install had bound on the engine under `app:<manifestId>`: script-action handlers, body hooks and bundle functions. With two packages each holding an action of one name on one object, a call that names no package kept being refused as ambiguous until the runtime restarted, and the uninstalled package's body hooks kept firing.

**The fix.**

- `@objectstack/runtime`: `unbindAppArtifactHandlers(ql, appId, { logger, source })` is the inverse of `bindAppArtifactHandlers`. It removes the actions, hooks and functions of the package's owner and of every owner the package's last bind on that engine recorded (a multi-package artifact's bodies), releases those owners' bare-name function claims, and forgets the bind record, so a later install binds as a first bind. Another package's handlers, host code and the environment's authored-action handlers are untouched. Jobs keep leaving through the `runtime.package-jobs` uninstall cleanup.
- `@objectstack/cloud-connection`: the uninstall door calls it right after the registry withdrawal, and not when the registry refuses the withdrawal (the package stays loaded then). A runtime that has no such export is warned with the remedy, as the install door already warns for a runtime with no binder.
- `@objectstack/objectql`: `removeActionsByPackage` hands a key back to the owner that still holds a handler for it. Each owner keeps its handler in its own package slot, but the slot a call that names no package runs held only the last registration. Removing that registration emptied the key, so the bare call answered "not found" while another owner still held a handler. The key now takes back the entry another coordinate's slot holds: the last coordinate holding the key in the order the slots were created, which is not always the last registration of this key. That choice matters only where the bare-call rule runs one of two owners, host code or a plugin beside one package on an object-bound key: when host code's slot was created first for another key but registered this key after the package, the hand-back runs the package's handler where a restart runs host code's. While two or more packages still hold the key, the bare call is refused naming them as before.

**Not changed.** `PATCH /api/v1/packages/:id/disable` leaves a disabled package's handlers in place, and the bare-call rule already counts no disabled package as an owner. `DELETE /api/v1/packages/:id` (the protocol's `deletePackage`) does not call this unbind, so it is unchanged.
