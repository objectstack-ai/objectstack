fix(runtime)!: an artifact holding two enabled jobs of one name schedules neither, refused at bind naming both, instead of the job service silently keeping the later one

Clause-②: no (narrowing) — `scheduleAppArtifactJobs` (the one binder `AppPlugin` and the install-local door schedule jobs through) answers an artifact whose enabled jobs share a name FROM both bound under one job-service key, the later replacing the earlier on every job service (`CronJobAdapter`, `IntervalJobAdapter`, `DbJobAdapter`), the earlier never running and nothing logged TO neither scheduled, each named in the new `refused` list of the result, and one `error` line per name carrying a `PackageScopedNameRefusedError` (`RESOURCE_CONFLICT`, 409, `ambiguous-in-environment`) whose message names every holder and how each job runs. That covers two package bodies declaring the name (a body-form or handler-form pair FROM one silently dropped; a pull pair FROM both runs refused 409 TO refused at bind), a package body and the artifact's top level outside every body (the residual: FROM, when the residual runs as the declaring body, the later job running and the other never; otherwise FROM the surviving run refused 409 TO refused at bind), and an artifact without `packages[]` listing the name twice (a JSON artifact no `defineStack` judged: FROM one silently dropped). A job of that name an earlier install of the package scheduled is cancelled with the rest (FROM kept running TO named in `cancelled`). A disabled twin collides with nothing and is not refused; its enabled twin is scheduled as before, and a pull's run keeps the attribution refusal it had. First-party census: 0 (the one first-party job, `showcase_health_sweep`, has its own name; `examples/app-multi-package` declares no job).
Metadata-protocol: none

**BREAKING** for an artifact whose enabled jobs share a name: two package bodies of one composition declaring the same job name, a package body and a manifest-less input of `composeStacks(…, { manifest: 'preserve' })` declaring it, or a hand-written or JSON artifact listing it twice. Before, the job service kept one of them under the shared name and the other never ran, with no log line; now neither is scheduled, and the boot (or the install-local rehydrate) logs the refusal at `error`, naming each holder. FROM two jobs sharing a name TO giving each its own name (`defineStack` already refuses the pair inside one stack). Code reading the `scheduleAppArtifactJobs` result gains the `refused` list beside `notScheduled`, `missingOrganization` and `failed`.
