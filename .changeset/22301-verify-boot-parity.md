`bootStack` mounts the providers an app's `requires` names, as `objectstack serve` does, and a cel-dated seed row reaches every hook in its stored form

Clause-②: yes (widening)

- **`@objectstack/verify`: `bootStack` boots what `requires` names.** The handle used to boot a fixed plugin set and ignore the app's `requires`, so an app's tests ran without services the same app gets on a real server (no record-change trigger fired on a write, the `approval` node had no service), and the app named the provider plugins by hand in `extraPlugins`. `bootStack` now reads `requires` by the rule `os serve` reads it with (the top-level list when present, otherwise each package body's) and mounts each token's provider from `os serve`'s own table. A provider the boot already holds is not constructed again: the harness's settings, analytics and sharing services, `automation: true`, and any `extraPlugins` entry that is the provider. A suite that passes its own instance keeps it, and the token's other plugins are skipped with it, as `os serve` skips them. The always-on providers a mounted provider hard-depends on come with it (`triggers` brings `job` and `queue`, `webhooks` brings `messaging`). Each provider is constructed with its own defaults, so a test never sends mail or SMS. A provider that cannot be constructed fails the boot, naming the token and the package. Every provider package in the table is now a dependency of `@objectstack/verify`. `@objectstack/cli` already depends on all of them.
- **What changes for an existing suite.** An app that declares `requires: ['automation', 'triggers']` now gets the automation service and the record-change trigger without `automation: true` or `extraPlugins`, so its record-triggered flows run on the handle's writes, as they do on a served app. Remove a provider from `extraPlugins` once the app declares its token. To keep a provider configured your own way, leave it in `extraPlugins`.
- **`@objectstack/core`: one home for the `requires` lookup.** `CAPABILITY_PROVIDERS`, `CapabilitySpec`, `CapabilityIdentities` and `providesCapability` (the token-to-provider table and its exact identity match) move here from the `Serve` command. So do `resolveStackCollection`, `stackDeclaredCapabilities`, `declaredPackageEntries`, `stackPackageBodies` and `collectFromPackageBodies` (the package-owned collection reader) from the CLI's utilities. `@objectstack/cli` depends on `@objectstack/verify`, so the handle could not read them where they were.
- **`@objectstack/cli`: no behaviour change.** `Serve.CAPABILITY_PROVIDERS` and `Serve.providesCapability` are now handles over the `@objectstack/core` declarations, and the CLI's `stack-collections` utilities re-export the moved readers.
- **`@objectstack/metadata-protocol`: a cel-dated seed value is handed over in its stored form.** `` cel`daysFromNow(n)` ``, `daysAgo(n)`, `today()` and `now()` resolve to a JS `Date`. The seed loader handed that `Date` to the engine, so what a hook saw depended on how the hook ran. An in-process `handler` (a source config, as `bootStack` boots it) saw the `Date` object. A sandboxed `body` (the compiled artifact `objectstack dev` boots) saw a full ISO instant, even on a `date` field. A hook that reads a date field as a string accepted the row under `objectstack dev` and refused it under `bootStack`. The loader now puts each `Date` on a `date`, `datetime` or `time` field into the stored form the drivers write (`YYYY-MM-DD`, the UTC ISO instant, `HH:MM:SS`) before any hook runs. Every hook then sees the value the column stores. A body hook on a `date` field now sees `2026-10-09` where it saw `2026-10-09T00:00:00.000Z`. Stored values on SQL drivers do not change. The in-memory driver now stores the string instead of a `Date` object.
