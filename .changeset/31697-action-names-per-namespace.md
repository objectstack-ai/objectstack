feat(objectql, runtime)!: object-less action names are held per namespace, and a call that names no package is refused when two holders answer it (ADR-0150 child B, #31697)

Clause-②: yes (narrowing) — a call that names no package is refused `409 RESOURCE_CONFLICT`, naming every holder, where it ran one of them before, in exactly two cases: two packages hold the action on one key (an object, or the object-less key), and, on the object-less key only, a package's beside host code or a plugin's. The doors: the engine's `executeAction`; the bare `POST /actions/:object/:action` and the MCP bare `run_action`; `GET /meta/action/NAME` for an object-less action; and, in process, the metadata service's own `get` / `getDiagnosed('action', NAME)` naming no package, for a name two packages hold. Also, a package that declares an object-less action named `install_package`, now a built-in name, is refused at install. Measured first-party: 0 (showcase, crm and multi-package booted: no object and name two holders answer, no owner-less declaration). The install side widens: two packages of two namespaces may each declare one object-less action name.
Metadata-protocol: added

**BREAKING** for a caller that names no package while two holders answer the name. Each such call is now refused `409 RESOURCE_CONFLICT` with a sentence naming every holder; nothing picks one by registration or listing order:

- `ObjectQL.executeAction(object, name, ctx)` with no `packageId`, while two packages' `app:<id>` handlers sit under `object:name`, or, for the object-less key (`global`), a package's beside host code (registered with no owner) or a plugin's. Before, the last registration ran. Host code or a plugin beside one package on an object-bound key still runs the last registration, as before. A handler the environment's authored-action resync registers (`metadata-service`) is never an owner.
- `POST /api/v1/actions/:object/:action[/:recordId]` (no namespace) and the MCP `run_action` with no `namespace`, while two packages declare the action on one object or on the object-less key, or, on the object-less key, a package's declaration stands beside an owner-less one the environment's store does not hold. Before, the object's own declaration (REST) or the first listed (MCP) answered.
- The metadata service's own `get` / `getDiagnosed('action', NAME)` with no package, in process, while two packages hold an action of the name. Its in-memory store keyed an action by name, so the package registered last had overwritten the other, and every read, including one naming the other package, answered the survivor. `action` is now a package-slotted store type beside `api`: each package's item keeps its own slot, a read naming a package answers that package's item (a package holding none answers nothing), the list shows both, and the read naming none is refused naming both. The store keys an action by its name, so this holds for two packages' actions bound to two different objects too. For that pair, `GET /meta/action/NAME?package=<id>` now serves that package's own body (it served the survivor's body under the asked package's stamp), and the bare `GET /meta/action/NAME` still answers `200` but serves the package registered first (the registry's answer) where it served the survivor. One holder per name reads exactly as before.
- `GET /api/v1/meta/action/NAME` with no `?package=`, while two packages hold an object-less action of the name, or a package's stands beside an owner-less item the environment's store does not hold. Before, the first registered or the owner-less item was served. A read of an action bound to an object is not refused (see the metadata-service bullet above for the pair of two packages' same-named actions on two objects).

The fix is the address that names the holder: `POST /api/v1/actions/:namespace/:object/:action`, `run_action` with `namespace`, `GET /api/v1/meta/action/NAME?package=<id>`, or `executeAction(object, name, ctx, { packageId })`, or `get('action', NAME, packageId)`. Renaming one of the two actions also works.

An owner-less declaration is the environment's only when the environment's own store holds it: an active `sys_metadata` row bound to no package with the same object (or none) and name, or an object row bound to no package that embeds the action. Then it answers first (ADR-0150 D3). Any other owner-less declaration is code the host or a plugin registered with no package: alone it answers; on the object-less key, beside a package's, it is refused, naming the package and the platform; on an object-bound key it is not judged, and the first declaration answers as before. The row's source decides, never a value in its definition.

Also changed, for a call that names no package on an object two declarations share and nothing is refused: the bare `POST /actions/:object/:action` now serves the declaration the MCP bare `run_action` serves. For a package's action embedded in an object beside the environment's own stored row of the same object and name, both now answer the environment's (ADR-0150 D3); before, both answered the embedded one.

A disabled package holds nothing at these doors: beside it, the enabled holder answers. When the listing behind the bare `POST /actions/:object/:action` cannot be read, the call answers `503` (the metadata plane is unavailable) instead of falling back to the object's own declaration.

The widening: the object-less `action` joins `NAMESPACE_SCOPED_BARE_NAME_TYPES` (ADR-0150 D2/D9). Two packages of two namespaces may each declare one object-less action name; the package door, the item seam and the cold boot accept the second, and the cold boot no longer warns about it. A co-owner of one namespace, a package with no namespace, two packages of `base`, `system` or `sys`, and a built-in name are refused as before. Console's bare calls to such a name answer 409 until Console carries the package: its navigation action items read `/meta/action/NAME` and its action buttons post `/actions/:object/:action` with no package. An action bound to an object was never covered and is unchanged.

`install_package` is a built-in object-less action name: the Console's marketplace and the cloud connection call `POST /actions/sys_package/install_package` by that fixed name, so a package that declares an object-less `install_package` is refused at install, naming the platform. No first-party package declares it.
