fix(metadata-protocol)!: a pair address (`?package=<base>.custom`, or the pair namespace's qualified path) reads the package it names, so its envelope is that package's and an App pair two of whose modules hold the name is refused naming both, never answered by the first registered holder (ADR-0150 D5, #32501)

Clause-②: yes (narrowing) — the App pair address `<App>.custom`, when two enabled modules of the App hold the name and one of them is the first registered package that ships it, is refused `409 RESOURCE_CONFLICT` naming both modules where it answered with the first registered module's item, on every door that reads it: `GET /meta/:type/:name?package=<App>.custom` and its `/layers`, and the qualified path `GET /meta/:type/<App namespace>_custom/:name` (the installed pair's namespace), on both transports; the dataset query doors `POST /analytics/dataset/query` and `/batch` with `?package=<App>.custom`, or `?callerPackage=<App>.custom` naming a pair the registry does not hold (nothing is run); the import doors' qualified `mappingName` `<App namespace>_custom/<name>` (nothing is written); and the publish probes' dataset read for a publish of an App pair the registry does not hold. `/layers` at an App pair that holds a stored row of a name two of its modules ship, when one of those modules is the first registered package that ships the name, is refused the same way where it reported that module's body as the code layer. With another package registered ahead of the modules, every one of these already answered the 409. The other moved answers keep their status and name the package the address reads in place of the first registered holder: the envelope (`_packageId`, `_packageVersion`, `_provenance`) of a base's pair address and of a stored row read at an exact address. Three widen from 404 to 200 on the same doors: the pair of an enabled base and an App pair one of whose two module holders is disabled, when the disabled holder registered first, and a row of a package that ships nothing beside a disabled shipper.
Metadata-protocol: none

**BREAKING** answer narrowing at the exact read (`@objectstack/metadata-protocol`), for the pair address of an App two of whose modules hold the name, on every door that reads that address.

- **Before → after, served → refused.** The App pair address, two enabled modules of the App holding the name and one of them the first registered package that ships it: 200 with the first registered module's item → `409 RESOURCE_CONFLICT`, `ambiguous-in-closure`, naming both modules. This holds on the real ObjectQL engine and on the bare `SchemaRegistry` composition alike; what decides the before is the registration shape: with another package registered ahead of the modules, the address already answered this 409. The doors that read the address, each with the same before and after:
  - `GET /meta/:type/:name?package=<App>.custom` and `GET /meta/:type/:name/layers?package=<App>.custom`;
  - the qualified path `GET /meta/:type/<App namespace>_custom/:name`, which names the same address once the pair is installed;
  - `POST /analytics/dataset/query?package=<App>.custom` and the same query in `/analytics/dataset/query/batch` (that query's entry): the first registered module's dataset was run → nothing is run. `?callerPackage=<App>.custom` naming a pair the registry does not hold reads as `?package=` and moves with it; with the pair installed, the caller arm already refused;
  - the import doors `POST /data/:object/import` and `/import/jobs` with the qualified `mappingName` `<App namespace>_custom/<name>`: the rows were imported through the first registered module's mapping → nothing is written;
  - the publish probes' dataset read, for a publish of an App pair the registry does not hold: the first registered module's dataset was probed → the widget is reported not probed. A publish of a registered pair resolves through the caller arm, which already refused.

  `/layers` at the App pair when the pair holds a stored row and two modules hold the name, one of them the first registered package that ships it: 200 with that module's body as `code` → the same 409; the plain read keeps serving the row, which is the pair's own and unambiguous, while the code layer has two holders. First-party callers: 0.
- **Before → after, same status, another package named.** A base's pair address (`?package=<base>.custom`, or the qualified path at `<base namespace>_custom`), another enabled holder of the name registered first: the base's body under the other holder's `_packageId`, `_packageVersion` and `_provenance` → under the base's. A stored row at an exact address: the base's override row at its pair, the same; a row bound only to a package that ships nothing, under the first registered shipper's envelope → its own stamp, no artifact envelope; the App pair's own row beside two module holders, under the first registered shipper's envelope → its own stamp. `/layers` at the base's pair and at a package that ships nothing already answered the base's code layer, or `code: null`, and does not move. The dataset and import doors run and import the same item as before, and the publish probes probe it. First-party callers: 0.
- **Before → after, widening.** A base's pair address, the base enabled and another holder of the name disabled and registered first: 404 → 200 with the base's item. The App pair address, one of two module holders disabled and registered first: 404 → 200 with the enabled module's item. Both on every door above: the dataset doors run the item where they answered 404, the import doors import through it where they answered `404 MAPPING_NOT_FOUND`, and the publish probes, for a pair the registry does not hold, probe it where they found nothing. `?package=<P>` and its `/layers`, where P ships nothing and holds a stored row of the name, its only shipper disabled: 404 (withheld by the disabled shipper's grafted stamp) → 200 with the row under its own stamp. First-party callers: 0.

**The remedy.** Read an item two modules of an App hold at the module's own address (`?package=<module>`, or the module's namespace in a qualified path or `mappingName`), as the refusal names.
