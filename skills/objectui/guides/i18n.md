# ObjectUI Internationalization (i18n)

Multi-language support via `@object-ui/i18n`.

## Setup

```typescript
import { I18nProvider, createI18n } from '@object-ui/i18n';

const i18n = createI18n({
  defaultLanguage: 'en',
  fallbackLanguage: 'en',
  detectBrowserLanguage: true,  // Auto-detect from navigator
  resources: {
    en: { common: { save: 'Save', cancel: 'Cancel' } },
    zh: { common: { save: '保存', cancel: '取消' } },
  },
});

function App() {
  return (
    <I18nProvider instance={i18n}>
      <AppContent />
    </I18nProvider>
  );
}
```

## Built-in locales

The package includes translations for:
- English (`en`), Chinese (`zh`), Japanese (`ja`), Korean (`ko`)
- German (`de`), French (`fr`), Spanish (`es`), Portuguese (`pt`)
- Russian (`ru`), Arabic (`ar`)

## useObjectTranslation hook

<!-- os:check -->
```typescript
import { useObjectTranslation } from '@object-ui/i18n';

function Header() {
  const { t, language, changeLanguage, direction } = useObjectTranslation();

  return (
    <header dir={direction}>
      <h1>{t('common.appTitle')}</h1>
      <select value={language} onChange={(e) => changeLanguage(e.target.value)}>
        <option value="en">English</option>
        <option value="zh">中文</option>
        <option value="ar">العربية</option>
      </select>
    </header>
  );
}
```

## Lazy language loading

For large apps, load translations on demand instead of bundling all locales:

```typescript
<I18nProvider
  config={{ defaultLanguage: 'en' }}
  loadLanguage={async (lang) => {
    const module = await import(`./locales/${lang}.json`);
    return module.default;
  }}
>
  <AppContent />
</I18nProvider>
```

## RTL (right-to-left) support

RTL is automatic for Arabic, Hebrew, and other RTL languages. The provider updates `document.dir` when the language changes.

```typescript
const { direction } = useObjectTranslation();
// direction: 'ltr' | 'rtl'
```

For Tailwind layout adjustments, use RTL-aware utilities:

```html
<!-- Automatically mirrors in RTL -->
<div className="ml-4 rtl:mr-4 rtl:ml-0">
  <span className="text-left rtl:text-right">Content</span>
</div>
```

## Number, date, and currency formatting

```typescript
import { formatCurrency, formatDate, formatNumber, formatRelativeTime } from '@object-ui/i18n';

function PriceDisplay({ amount, currency, date }) {
  return (
    <div>
      <p>{formatCurrency(amount, { currency })}</p>        {/* $1,234.56 or ¥1,234.56 */}
      <p>{formatDate(date, { style: 'short' })}</p>           {/* 2024-03-15 */}
      <p>{formatNumber(1234567)}</p>                      {/* 1,234,567 or 1.234.567 */}
      <p>{formatRelativeTime(date)}</p>                   {/* "3 days ago" */}
    </div>
  );
}
```

## Schema-level i18n

A display label in an ObjectUI schema — `label`, `title`, `subtitle`, `description` — takes
one of two forms authorized by `@objectstack/spec`. Both are real; neither is deprecated.

**Form 1 — a plain string**, the default-language literal. Its translations live in a
translation bundle, so resolve them before passing the schema to SchemaRenderer:

```typescript
const { t } = useObjectTranslation();

const localizedSchema = {
  type: 'card',
  // Keys sit on the node — the renderers read `schema.title` / `schema.label`,
  // not a `props` envelope.
  title: t('customers.title'),
  description: t('customers.description'),
  children: [
    { type: 'button', label: t('common.save') },
    { type: 'button', label: t('common.cancel') },
  ],
};
```

**Form 2 — an inline locale map**, every language written inline and keyed by BCP-47 tags
(`en`, `zh-CN`, `ja-JP`) or `default`. The renderer picks the entry for the active language
at display time via `pickLocalized`, so there is no bundle key and no `t()` pass:

<!-- os:check -->
```typescript
const localizedSchema = {
  type: 'card',
  title: { en: 'Customers', 'zh-CN': '客户' },
  children: [
    { type: 'button', label: { en: 'Save', 'zh-CN': '保存' } },
    { type: 'button', label: { en: 'Cancel', default: 'Cancel' } },
  ],
};
```

Prefer the bundle route for an app with many strings — it is the one that scales, because
translators never touch the page modules. Reach for the inline map when a label's
translations belong with the metadata that declares it, which is how server-driven metadata
that travels without a bundle carries its own languages.

## Language-aware + responsive page

When combining with `@object-ui/mobile` for responsive layouts:

```typescript
import { I18nProvider } from '@object-ui/i18n';
import { useBreakpoint } from '@object-ui/mobile';
import { SchemaRendererProvider, SchemaRenderer } from '@object-ui/react';

function App() {
  const { isMobile } = useBreakpoint();
  const schema = isMobile ? mobilePageSchema : desktopPageSchema;

  return (
    <I18nProvider config={{ defaultLanguage: 'en' }}>
      <SchemaRendererProvider dataSource={data}>
        <SchemaRenderer schema={schema} />
      </SchemaRendererProvider>
    </I18nProvider>
  );
}
```

## Common mistakes

- Bundling all locale files upfront — use lazy loading for apps with many languages.
- Forgetting `dir={direction}` on root elements — RTL layout won't apply.
- Using `{key, defaultValue}` translation objects — that key-reference vocabulary was retired.
  `@objectstack/spec` rejects the object with its own message: *an inline
  label map is keyed by BCP-47 locale tags (`en`, `zh-CN`, …) or `default` — not by
  `key`/`defaultValue`*. Nothing catches it at render time either: `pickLocalized` falls
  through to the first string value, so the screen shows the raw key (`common.save`).
