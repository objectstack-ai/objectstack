A **Page** defines a custom UI layout using components, regions, and variables. Unlike Views which are bound to a single Object, Pages are flexible containers that can combine multiple components, embed views, and manage local state.

## Basic Structure

{/* os:check */}
```typescript
const homePage = {
  name: 'sales_home',
  label: 'Sales Home',
  type: 'home',
  regions: [
    {
      name: 'header',
      width: 'full',
      components: [
        {
          type: 'metric_card',
          id: 'total_revenue',
          label: 'Total Revenue',
          properties: {
            object: 'opportunity',
            field: 'amount',
            aggregate: 'sum',
            format: 'currency',
          },
        },
      ],
    },
    {
      name: 'main',
      components: [
        {
          type: 'list_view',
          id: 'recent_deals',
          label: 'Recent Deals',
          properties: {
            object: 'opportunity',
            view: 'recent_open',
            limit: 10,
          },
        },
      ],
    },
  ],
};
```

## Page Properties

| Property | Type | Required | Description |
| :--- | :--- | :--- | :--- |
| `name` | `string` | ✅ | Machine name (`snake_case`) |
| `label` | `string` | ✅ | Display label |
| `description` | `string` | optional | Page description |
| `type` | `enum` | optional | Page type (see below; default `'record'`) |
| `object` | `string` | optional | Associated object (for `record` type) |
| `record` | `{ object, view?, filter?, sort? }` | optional | The row an `app` page is about: the FIRST row of this query, read under the caller's identity, which every component `visibleWhen` on the page reads as `record`. A count or a plan is a field on that row — a `summary` roll-up (`record.environment_count > 1`) or the object's own field (`record.plan != 'free'`). **Refused on any page that is not `type: 'app'`** (a record page's row is the record it opens). Planned in the renderer: until the console mounts it, `record` stays unbound on an `app` page |
| `template` | `enum` | optional | Layout template: `'default'` (the default), `'header-sidebar-main'`, `'three-column'` or `'dashboard'` — see [Templates](#templates). Any other name is refused |
| `kind` | `enum` | optional | Page override mode (default `'full'`). `full` \| `slotted` = structured authoring; `html` = author-written constrained JSX/HTML compiled (parsed, never executed) to the tree (ADR-0080; ADR-0081 named it `html`); `react` = real-React source executed at render by the runtime (ADR-0081) — it runs author JS, so it is gated by a host capability that defaults ON and is disabled server-side via `OS_PAGE_REACT=off`. See [Authoring modes](#authoring-modes) |
| `regions` | `PageRegion[]` | optional | Layout regions with components (default `[]` — `list` pages render via `interfaceConfig`, and an empty `record`/`home`/`app` page falls back to the synthesized default layout) |
| `slots` | `object` | optional | Slot overrides for a `kind: 'slotted'` record page — see [Slotted pages](#slotted-pages) |
| `source` | `string` | optional | Page source text — required (and authoritative over `regions`) when `kind` is `'html'` or `'react'`. For `kind: 'html'` it is constrained JSX/HTML compiled to the tree by `@objectstack/sdui-parser` at save time (parse, never execute). For `kind: 'react'` it is real React/JSX executed at render by `@object-ui/react-runtime` (trusted tier). See [React Pages](/docs/ui/react-pages) |
| `variables` | `PageVariable[]` | optional | Local state variables |
| `isDefault` | `boolean` | optional | The default record page of its `object` — the page that object's record view opens. At most one `isDefault: true` record page per object per deployment: a second is refused by `defineStack` / `os validate`, at package registration and at metadata save, naming both pages. Saving a page under the existing default's own name is that page, not a second default. **Refused on any other page** (a `home`, `app`, `utility` or `list` page, or a record page with no `object`): nothing reads it there. A page does not choose where an app opens — see [Page Types](#page-types) |

### Page Types

| Type | Description | Use Case |
| :--- | :--- | :--- |
| `record` | Tied to a specific object record | Custom detail pages |
| `home` | Region page at the widest content width | Overviews and start pages |
| `app` | Region page at app content width | Custom layouts |
| `utility` | Region page at the narrowest content width, inline in the main column | Tools, settings, wizards |
| `list` | Record list/interface surface | Data-driven interface pages |

`home`, `app` and `utility` render the same way — the page's regions, laid out by its
`template` — and differ only in how wide the content runs. **A `home` page is not a landing
declaration:** an app opens on its **first navigation item** (by `order`), so to make a page
the one an app opens, put its navigation entry first; the root landing follows the app's own
`isDefault`. A `utility` page is an ordinary inline page — there is no floating panel or
utility bar that hosts it — and it cannot be a print page.

Earlier roadmap types (`dashboard`, `form`, `record_detail`, `record_review`, `overview`, `blank`) were **removed from the schema** because they never shipped a renderer (ADR-0049 enforce-or-remove); only the five types above are valid.

## Authoring modes [#authoring-modes]

A page's `kind` selects **how the body is authored**. Three modes ship, and the rest of
this page describes the first one:

| `kind` | You write | Executed? | Reach for it when |
| :--- | :--- | :--- | :--- |
| `full` (default) / `slotted` | Structured `regions` / `slots` of components — *the rest of this page* | — | Record, home and app layouts assembled from the component catalogue |
| `html` | A `source` string of constrained JSX: registered components plus safe native HTML | **No** — parsed into the same component tree at save time by `@objectstack/sdui-parser` | Free-form layout, landing pages and composed dashboards, including author- or AI-generated ones you have not reviewed |
| `react` | A `source` string of real React — hooks, handlers, arbitrary JS | **Yes** — in the app's own React tree, no sandbox | Interactive business UIs — master/detail, wizards, state-driven filters — written by authors you trust |

The two source tiers set `source` instead of `regions`. **`source` is authoritative over
`regions`**: when both are present the source wins, and `regions` holds at most a derived
cache of it. A page whose `kind` is `html` or `react` with no non-empty `source`
is rejected by the schema rather than rendering empty.

`'jsx'`, the tier's first name, was retired in `@objectstack/spec` 18: an authored
`kind: 'jsx'` is refused with the prescription naming `'html'`. Stored pages written as
`'jsx'` keep loading as `html` pages.

Because `kind: 'react'` executes author JavaScript, it is gated by a host capability that
defaults **OFF** and is turned on server-side per deployment with
`OS_PAGE_REACT_ENABLED=true`. The `html` tier is unaffected by that switch — it is never
executed.

<Callout type="warn">
Neither source tier is styled with Tailwind utility classes. A page's `source` is
*runtime metadata*, and the console's build-time Tailwind scans only the console's own
source — so a utility class name in page source silently produces no CSS, with no error
(ADR-0065). Style an `html` page with its components' structured props and a JSON `style`
object; style a `react` page with inline `style={{ … }}` and `hsl(var(--token))` theme
colors.
</Callout>

Both tiers are checked at author time — block props, field bindings and source syntax —
by `os validate`, `os lint` and `os build` alike. See
[React Pages](/docs/ui/react-pages) for the full authoring guide and
[Validating metadata](/docs/deployment/validating-metadata) for the rules.

## Regions

Regions define layout zones on the page. Each region contains components, and its `name`
is the slot of the page's `template` it fills.

{/* os:check */}
```typescript
regions: [
  {
    name: 'sidebar',
    width: 'small',
    components: [/* ... */],
  },
  {
    name: 'main',
    components: [/* ... */],
  },
]
```

| Property | Type | Required | Description |
| :--- | :--- | :--- | :--- |
| `name` | `string` | ✅ | The template slot the region fills (see [Templates](#templates)); a name the template does not place is refused |
| `width` | `enum` | optional | `'small'`, `'medium'`, `'large'`, `'full'`. A region named `main` takes only `'full'`, which is page-wide: the page drops its max-width cap and fills the screen. `main` is drawn at the width its template leaves it, so `'small'`, `'medium'` and `'large'` are refused there |
| `components` | `PageComponent[]` | ✅ | Components in this region |

### Templates

A page's `template` decides where each region is drawn. Each template places a fixed set of
region names (`PAGE_TEMPLATE_SLOTS` in `@objectstack/spec/ui`); names match
case-insensitively.

| Template | Regions it places |
| :--- | :--- |
| `default` | `header`, `sidebar`, `main`, `aside`, `footer` — `sidebar` and `aside` beside `main`, `header` and `footer` spanning it |
| `header-sidebar-main` | `header`, `sidebar`, `main` |
| `three-column` | `header`, `sidebar`, `main`, `aside`, `footer` |
| `dashboard` | `header`, `footer`, and **any other name** — every other region is a grid cell |

On a `kind: 'full'` page, a region its template does not place — `left_sidebar`,
`right_sidebar`, `content` — is refused by `os validate`, `os build` and the metadata save door,
naming the template's slots: the console would stack it under `main` at full width and ignore
its `width`. Use `sidebar` for the left column and `aside` for the right. Each slot takes one
region: a second `main` (or, on `dashboard`, a second `header` or `footer`) is not drawn at all,
and is refused the same way. `full-width` is no
longer a template name: it was a second name for `default`, and is refused with that
replacement.

## Record pages

### The synthesized default

A record page needs no authoring. With no page assigned, the Console synthesizes one from
the object: a header, the highlights strip, a tab strip and the discussion panel. The strip
is **Details**, then one tab per relationship whose child field declares
`relatedList: 'primary'`, then a shared **Related** tab for the other related lists, then
**History**; an object with `enable: { files: true }` also gets an **Attachments** tab with a
count badge. Promoting a child table to its own tab is therefore a one-word change on the
relationship field, not a page-authoring task, and `relatedList: false` leaves a child off
the page.

The Console lays the page out by the width of the surface it occupies (the drawer, the
split pane or the full page), never by the viewport. From 1280 px the tabs become three
columns: details, a timeline (the discussion composer, then Activity and History) and the
related lists as cards with Approvals, Attachments and the created/updated line. From
1024 px the related column folds into a rail behind a **Related (N)** toggle. Below that, and
always in a drawer or split pane, the tab strip is drawn. `?tab=` selects a tab in the strip.

### Slotted pages

`kind: 'slotted'` overrides only the parts of the synthesized page you name, and the
synthesizer fills in the rest. A slotted page authors `slots`, not `regions`:

| Slot | Replaces |
| :--- | :--- |
| `header` | The `page:header` node |
| `actions` | The action bar (`record:quick_actions`) |
| `alerts` | The alert banners above the body |
| `highlights` | The highlights strip |
| `details` | The body of the Details tab; the other tabs stay synthesized |
| `discussion` | The discussion panel |

Each slot takes one component or an array of them, and replaces its part whole: there is no
deep merge. There is no `tabs` slot: the tab strip is composed from the object's roles and
relationship flags. To change which related lists appear or their order, set `relatedList` /
`relatedList: 'primary'` on the child's reference field; a page that needs its own strip is
`kind: 'full'`, drawn as authored. `slots.tabs`, `slots.related` and `slots.relatedLists` are
refused by name, and `os migrate meta --from 17` drops a stored `slots.tabs`.

{/* os:check */}
```typescript
const accountDetailPage = {
  name: 'account_detail_page',
  label: 'Account Detail',
  type: 'record',
  object: 'account',
  kind: 'slotted',
  regions: [],
  slots: {
    header: {
      type: 'page:header',
      properties: { title: '{name}', subtitle: '{industry} · {type}' },
    },
  },
};
```

Use a slotted page to change one or two parts of an otherwise standard record page, and a
`full` page for a record page that looks nothing like the default.

### The discussion panel is composed, never appended

A record page shows a discussion panel if and only if the page composes a
`record:discussion` node (or `record:chatter`, the same block under another name).
Synthesized and slotted pages compose it for you; a `full` page places it like any other
block, and the node's own properties are honoured, so
`{ type: 'record:discussion', properties: { feed: { showCommentInput: false } } }` draws the
conversation without a composer. The object outranks the page: `enable: { feeds: false }`
suppresses the panel whether or not the page composes it, and the server refuses comments on
such an object (`403 FEEDS_DISABLED`).

### Related lists

- **Permission-gated.** A relationship whose child object the user cannot read produces no
  tab and no section, and a `record:related_list` on an authored page hides itself the same
  way.
- **Paged.** A related list shows `limit` rows per page (5 unless set), fetched a page at a
  time with the count badge showing the whole collection; `sort` pins the initial order, and
  a user's column sort is sent to the server. A list that declares `columns` fetches only the
  declared columns the user can read.
- **Actions are ids.** By default a related list draws the child object's own actions: those
  placed at `list_toolbar` as header buttons, and those at `list_item` or `record_related` in
  each row's menu (`record_related` shows only inside a parent record). Declaring
  `actions: ['export_contacts', 'send_welcome']` in the block's `properties` replaces that
  set, in that order; each action is still placed by its own `locations`, and `[]` shows
  none. New, Edit, Delete and opening a row are not actions: they follow the object's
  `userActions` and the user's permissions. An id that names no action of the child, or one
  with no list location, shows a notice naming it rather than being dropped.

### The page header

`page:header` is the title bar. Its props go in `properties`, and the shape is closed, so an
unknown or retired key (`description`, `icon`, `breadcrumb`, `showStar`) is refused by name.

| Property | Default | Description |
| :--- | :--- | :--- |
| `title` | Derived from the record on a record page | Heading; `{field}` tokens interpolate against the record, and a token that resolves to nothing renders empty. Set it on a non-record page |
| `subtitle` | — | The line under the title, interpolated the same way |
| `actions` | — | Ids of actions declared on the page's object. An authored list is the whole set: an action that declares `record_header` but is not named is not drawn, and omitting the key draws none of the object's actions. Only the synthesized page draws every `record_header` / `record_more` action |
| `recordChrome` | `true` | Draw the title as the record chip (object label, copy-id button, the record's picture when the object names an `imageField`); `false` keeps a bare heading |
| `showCopyId` | `true` | The copy-record-id button in the chip |
| `maxVisible` / `mobileMaxVisible` | 3 / 1 | How many actions render inline before the rest fold into the `⋯` menu |
| `aria` | — | ARIA attributes (`ariaLabel`, `ariaDescribedBy`, …) for the `<header>` element |

A named action renders only if its `locations` include `record_header` (inline) or
`record_more` (straight into `⋯`); an id that names no action renders nothing and is reported
once in the browser console. Which actions take the inline slots is metadata too: actions are
sorted by `order` (lower first; the host's Edit / Share / Delete use 100 and above, so
authored actions outrank them), `variant: 'primary'` breaks ties, `variant: 'danger'` draws a
red button or a red row at the foot of the `⋯` menu, and `component: 'action:menu'` pins an
action inside `⋯`. Past the `⋯` menu a record page shows a **⟳ refresh** button: it is
chrome, not an action, so it has no metadata key, is never folded into `⋯`, and re-reads the
record, its related lists and tab badges in place without losing the open tab or an inline
edit.

A page has one `<h1>`. On a record page the header owns it; on another page type a
`page:header` with a literal title becomes the page heading. `page:header` draws no
children: anything that belongs beside it goes in a sibling node.

## Components

Components are the building blocks placed inside regions.

```typescript
{
  type: 'chart',
  id: 'revenue_chart',
  label: 'Revenue Trend',
  properties: {
    chartType: 'line',
    object: 'opportunity',
    categoryField: 'close_date',
    valueField: 'amount',
  },
  events: {
    onClick: "navigate_to('opportunity_detail', { id: $event.id })",
  },
  visibleWhen: "'sales_manager' in current_user.positions",
  style: { height: '400px' },
}
```

| Property | Type | Required | Description |
| :--- | :--- | :--- | :--- |
| `type` | `string` | ✅ | Component type (standard `PageComponentType` enum or custom string) |
| `id` | `string` | optional | Unique component instance identifier |
| `label` | `string` | optional | Display label |
| `properties` | `Record<string, unknown>` | optional | Component-specific configuration (default `{}` — many components carry no props) |
| `events` | `Record<string, string>` | optional | Event handlers (action expressions) |
| `style` | `object` | optional | CSS styles |
| `className` | `string` | optional | CSS class names |
| `responsiveStyles` | `object` | optional | **Preferred** SDUI styling channel (ADR-0065): **desktop-first** per-breakpoint scoped style maps, compiled to id-scoped CSS at render. Keys are `large` (the unconditional base), then `medium` / `small` / `xsmall` as `max-width` overrides. Prefer design tokens, e.g. `{ large: { padding: 'var(--space-8)' }, small: { padding: 'var(--space-4)' } }`. Use over ad-hoc `style` / `className` for metadata-authored pages. |
| `visibleWhen` | `string` | optional | Visibility predicate (CEL) — component renders only when the expression is `true`. Binds `record` (the record a `record` page opens, or the row an `app` page's `record` binding reads — a block's own `dataSource` binds none for its siblings), `current_user`, and page state as `page.<var>`. A plan is not `features.*` — those are the deployment's public auth flags, the same for every organisation; read it off the page's row. The retired spelling `visibility` is refused at parse (ADR-0089 D2). |

The `type` field is a union of the standard `PageComponentType` enum and any custom string. The standard (namespaced) component types include:

- **Structure:** `page:header`, `page:footer`, `page:sidebar`, `page:tabs`, `page:accordion`, `page:card`, `page:section`
- **Record context:** `record:details`, `record:highlights`, `record:related_list`, `record:activity`, `record:chatter`, `record:path`, `record:alert`, `record:quick_actions`, `record:reference_rail`, `record:history` — each renders from the record context a **record page** mounts, so they belong on a `type:'record'` page. A `kind:'react'` page mounts no such context and `os validate` rejects them there (see Validating metadata §10b)
- **Navigation:** `app:launcher`, `nav:menu`, `nav:breadcrumb`
- **Utility:** `global:search`, `global:notifications` — `user:profile` is **not** author-placeable: it is shell chrome (the signed-in user's avatar menu, which the app shell renders itself on every page), no renderer exists for it by ruling (objectstack#14159 / objectui#7135), and an authored `user:profile` node is refused at the schema door — `definePage()`, `os validate`, `os build` — with that prescription at the node's path instead of drawing an unknown-type panel in front of a user
- **AI:** `ai:suggestion` — `ai:chat_window` was retired in v17.x: AI chat is not a page element, and the floating chat overlay the console mounts on every page is the supported entry point (set the app's `defaultAgent` to choose which platform agent answers there). No renderer for it ever shipped, and an authored `ai:chat_window` node is refused at the schema door — `definePage()`, `os validate`, `os build` — with that prescription at the node's path instead of drawing an unknown-type panel in front of a user
- **Elements:** `element:text`, `element:number`, `element:image`, `element:divider`, `element:button`, `element:record_picker`, `element:text_input` (`element:filter` and `element:form` were retired in v17.x — no renderer ever shipped for either, and an authored node of either type is refused at the schema door — `definePage()`, `os validate`, `os build` — with that prescription at the node's path, bare node included. List surfaces own their filtering via a view's `userFilters` quick-filter bar or the list toolbar's filter builder; for forms use the object-bound `object-form` block, which is rendered and designer-publishable)

Components may also carry `dataSource` (a per-element data binding — see below), `responsiveStyles` (per-breakpoint scoped CSS, ADR-0065), and `aria` configuration. Custom string types are also accepted for project-specific widgets. (The former `responsive` layout block was retired in v17.x — no renderer ever applied it; see the upgrade guide.)

### Element data sources

A component's `dataSource` takes one of two shapes. The **object** binding queries an object, overriding the page's own `object`, so one page can show several objects. The **API** binding reads one endpoint on the deployment's own origin and binds its answer, so a page can compose from a summary that is not an object:

{/* os:check */}
```typescript
import type { PageComponent } from '@objectstack/spec/ui';

// Object binding: `object` is required; `view`, `filter`, `sort` and `limit` narrow it.
const openDeals: PageComponent = {
  type: 'list-view',
  dataSource: {
    object: 'opportunity',
    view: 'open_deals',
    filter: [{ field: 'amount', operator: 'greater_than', value: 10000 }],
    limit: 10,
  },
};

// API binding: `read.url` is a same-origin API path; `path` selects the part
// of the `{ success, data }` response the element binds.
const environments: PageComponent = {
  type: 'stat',
  dataSource: {
    provider: 'api',
    read: { url: '/api/v1/cloud/home' },
    path: 'data.environments',
  },
};
```

The API binding's rules:

- **Same-origin only.** `read.url` must open with a single `/`. An absolute URL of any scheme (`https:`, `mailto:`, `javascript:`, …), a protocol-relative `//host`, a backslash the browser reads as a slash, a space or control character, and a relative path such as `./home` are all refused when the page is parsed (`definePage()`, `os validate`, `os build`), with the reason.
- **No credentials in metadata.** The console reads the endpoint with its own signed-in fetch, so the read block has no `headers`, and a credential key such as `headers`, `credentials` or `token` is refused.
- **Reads only.** `read.method` is optional and accepts `GET` alone; there is no `write` block.
- **Rendered by the console.** The console reads the binding on every page element and binds the selected value as `data`: in the element's expression holes (`${data.used}`), in its `visibleWhen`, and in every element nested inside it. The console's generic `hero`, `stat`, `usage-bar`, `checklist` and `tile-grid` blocks are built to take it as their `dataSource`. While the read is in flight the element shows a loading panel, and a refused binding or a failed read shows an error panel instead.

### Expression holes in element properties

A string in an element's `properties` may carry `${…}` holes, which the Console fills when
it renders: `"content": "Welcome back, ${current_user.name}"`. The roots are `record` (the
page's row), `current_user`, `page.<var>` for page variables and, under an element with an
API `dataSource`, `data`. An inline locale map is filled member by member and then drawn in
the viewer's language:

```json
{
  "type": "element:text",
  "properties": {
    "content": { "en": "Welcome back, ${current_user.name}", "zh-CN": "欢迎回来,${current_user.name}" }
  }
}
```

A hole whose member is missing renders empty; a hole whose root does not exist renders as
its own source text, with one line in the browser console. Holes fill copy; they are not
gates. A component's `visibleWhen` is a CEL predicate over the same roots
(`"'sales_manager' in current_user.positions"`), not a `${…}` template.

### List blocks in a region

A region page sizes each block to its region, measured from the rendered width (no key sets
it). A `list-view` in a region narrower than half the page, such as an `aside` beside `main`,
renders a compact list: the title and record count, then two-line rows from the view's first
two visible columns. A region half the page or wider renders a capped table: at most the
block's `dataSource.limit` rows (5 when unset) and the view's first four visible columns.
Neither draws a toolbar, view tabs or a pager; both end with a **View all** link, to the
saved view's page when the block binds `dataSource.view` and to the object's list otherwise
(the block's own filter and sort are not carried, so bind a saved view to link to exactly
what the block shows). `html` and `react` pages have no regions, so their list blocks render
the whole list. A `page:tabs` block whose tabs hold list blocks badges each tab with its
list's record count before it is opened; a tab item's own `count` wins.

## Variables

Pages can define local variables for managing state across components.

{/* os:check */}
```typescript
variables: [
  {
    name: 'selected_tab',
    type: 'string',
    defaultValue: 'overview',
  },
  {
    name: 'date_range',
    type: 'object',
    defaultValue: { start: null, end: null },
  },
]
```

Variable `type` accepts `'string'` (default), `'number'`, `'boolean'`, `'object'`, `'array'`, or `'record_id'`.

## Complete Example

{/* os:check */}
```typescript
const accountRecordPage = {
  name: 'account_detail',
  label: 'Account Detail',
  type: 'record',
  object: 'account',
  variables: [
    { name: 'active_tab', type: 'string', defaultValue: 'details' },
  ],
  regions: [
    {
      name: 'header',
      width: 'full',
      components: [
        {
          type: 'record:highlights',
          id: 'header',
          properties: {
            fields: ['name', 'type', 'industry', 'owner'],
          },
        },
        // Record actions are their own component — `record:highlights` renders
        // field chips and nothing else.
        {
          type: 'record:quick_actions',
          properties: {
            actionNames: ['edit', 'delete', 'clone'],
          },
        },
      ],
    },
    {
      name: 'sidebar',
      width: 'small',
      components: [
        {
          type: 'record:details',
          id: 'key_fields',
          label: 'Key Fields',
          properties: {
            fields: ['annual_revenue', 'employees', 'website', 'phone'],
          },
        },
        {
          type: 'record:activity',

      ],
    },
    {
      name: 'main',
```
