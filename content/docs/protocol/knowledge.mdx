ObjectStack does not ship its own RAG engine. The market has many mature
options (RAGFlow, LlamaIndex, Dify, Vectara, pgvector + custom pipelines)
and competing with them on chunking, embeddings, hybrid retrieval, and
rerankers is not where the framework can add value.

Instead, the framework defines a thin **Knowledge Protocol** — a
spec-level contract for knowledge sources, documents, hits, and the
service that orchestrates them — and ships individual adapters as
**plugins**. This mirrors the same pattern already proven by
`IDataEngine` / driver plugins (`driver-sql`, `driver-mongodb`,
`driver-memory`) and `IStorageService` / S3 + local FS adapters.

<Callout type="info">
The Knowledge Protocol contract and the `service-knowledge` orchestrator are open
framework mechanisms. The AI **consumer** that wires the `search_knowledge` tool
into an in-product chat loop (shown below) ships in
**ObjectOS**. On the open-source framework, reach your data through `@objectstack/mcp`
(BYO-AI) instead: its door serves the same `search_knowledge` tool wherever the
knowledge service is installed, searching only the sources whose `aiExposed` is
not `false`, as the caller.
</Callout>

This document describes the **why**, the **contract**, the **plugin
model**, and the **MVP scope** that ships in Phase 1.

---

## 1. Why a protocol, not a built-in engine

Building our own RAG engine would force us to compete on three fronts
where dedicated projects already win:

- **Document understanding** — PDF/scan/table extraction (DeepDoc,
  LlamaParse).
- **Retrieval quality** — hybrid vector + BM25, MMR, rerankers.
- **Operations** — knowledge base UI, embedding cost tracking, batch
  reindex jobs.

We have nothing distinctive to add to those layers. We **do** have
distinctive value to add **around** them:

1. **Metadata-native sources.** ObjectQL objects are first-class
   knowledge sources. Records become documents automatically, with no
   ETL.
2. **Permission-aware retrieval.** Every search is scoped to the
   caller's `ExecutionContext` so RLS naturally applies — the same
   policy that protects REST and ObjectQL queries also protects what
   the LLM can read.
3. **Realtime sync.** ObjectQL `data.record.*` events drive incremental
   reindex without manual cron jobs.
4. **Unified audit + observability.** Knowledge searches participate in
   the same trace / audit pipeline as REST, ObjectQL, and tool calls.

The protocol scopes the framework's responsibility to (1)–(4) and
delegates the rest to plugins.

## 3. Protocol surface

### 3.1 `KnowledgeSource` (declarative metadata)

A `KnowledgeSource` describes *what* to index and *which adapter* to
use. It is stored as metadata (versioned, environment-scoped) just
like a view or a flow.

Three source kinds:

| Kind     | Origin                                              | Example use case                |
|----------|-----------------------------------------------------|---------------------------------|
| `object` | An ObjectQL object — each record becomes a document | Customer notes, KB articles     |
| `file`   | A folder in `IStorageService`                       | Onboarded PDFs, uploads         |
| `http`   | A list of remote URLs                               | External docs, RSS, sitemaps    |

`kind` is the discriminator, and each kind carries its own keys — a key from one
kind is rejected on another:

```typescript
// object — content comes from the named fields of each matching record
source: {
  kind: 'object',
  object: 'kb_article',
  contentFields: ['title', 'body'],       // at least one, required
  metadataFields: ['category', 'author'], // optional, carried onto the document
  where: { status: 'published' },         // optional ObjectQL filter
}

// file — every object under a storage prefix
source: {
  kind: 'file',
  prefix: 'knowledge/handbook/',
  mimeTypes: ['application/pdf', 'text/markdown'], // optional; omit to take all
}

// http — an explicit URL list (each must be a valid URL)
source: {
  kind: 'http',
  urls: ['https://docs.example.com/guide', 'https://docs.example.com/faq'],
  userAgent: 'ObjectStack-KnowledgeBot/1.0', // optional
}
```

Every source binds to a named **adapter id** (e.g. `'ragflow'`,
`'memory'`). The adapter id is resolved at runtime by the plugin that
registers itself with that name. Adapter config (endpoint, dataset id,
…) is passed through opaquely.

### 3.2 `KnowledgeDocument`, `KnowledgeChunk`, `KnowledgeHit`

Canonical shapes shared by every adapter:

- `KnowledgeDocument` — one logical document (`id`, `sourceId`,
  `sourceRecordId?`, `content`, `metadata`, `permissions?`,
  `organizationId?`, `docHash?`). `organizationId` is the organization of
  the record the document was assembled from: the service sets it from the
  record's `organization_id` under a walled tenancy posture (`group` or
  `isolated`), and leaves it absent under `single`, for `file` / `http`
  sources and for a record with no organization — see
  [Organization scope](#organization-scope). `docHash` is a hash of the
  assembled document — content, title and metadata, and the organization
  when the document has one, in a stable key order, behind a version prefix
  (`v1:`). The service computes both on every document it hands an adapter,
  and `indexDocument` refuses a document that already carries either; the
  adapter stores them and returns `docHash` as stored, and never computes or
  alters either.
- `KnowledgeChunk` — adapter-produced chunk of a document. The framework
  does **not** chunk; adapters do.
- `KnowledgeHit` — a search result (`chunkId`, `documentId`, `score`,
  `snippet`, `sourceRecordId?`, `metadata`).

The `sourceRecordId` field is the linchpin of permission-aware
retrieval: when a hit references an ObjectQL record, the
`KnowledgeService` re-checks it through `dataEngine.find` with the
caller's `ExecutionContext` and drops hits the user is not allowed to
read. **A hit that the user could not have queried directly is never
returned.**

The re-check runs after ranking, so the service asks for more than it
answers. For a caller who is not the system identity, each `object`
source is asked for `topK × 5` hits. When fewer than `topK` survive the
re-check, every `object` source that answered as many hits as it was asked
is asked once more, for `topK × 20`. That is the cap: a caller who may read
fewer matching rows than survive within it gets fewer than `topK` hits. An
adapter that answers fewer than it was asked (one that caps `topK`) is not
asked again. A `file` or `http` source is asked for `topK` once, and so is
every source for the system identity. The answer is at most `topK` hits.
How many hits the re-check removed is logged at `debug`, never returned to
the caller.

A hit's `title` is the value of the object's display field (ADR-0079
`resolveDisplayField`: `nameField`, else the derived title field), set
when the document is built. It is empty when that field is a
credential-class or `internal` field, when the value is empty, and when
the object resolves no display field. A source over an object with no
registered definition reads a field named `title`.

### 3.3 `IKnowledgeService` (consumed by the ObjectOS AI runtime, REST, Console)

```ts
interface IKnowledgeService {
  // Adapters
  registerAdapter(id: string, adapter: IKnowledgeAdapter): void;
  getAdapter(id: string): IKnowledgeAdapter;
  listAdapters(): string[];

  // Sources
  registerSource(source: KnowledgeSource): void;
  unregisterSource(sourceId: string): void;
  listSources(): KnowledgeSource[];
  getSource(sourceId: string): KnowledgeSource | undefined;

  // Documents
  indexDocument(sourceId: string, doc: KnowledgeDocument): Promise<void>;
  deleteDocument(sourceId: string, documentId: string): Promise<void>;
  reindexSource(sourceId: string, opts?: KnowledgeReindexOptions): Promise<KnowledgeReindexResult>;

  // Search
  search(query: string, opts?: KnowledgeSearchOptions): Promise<KnowledgeHit[]>;
}
```

`KnowledgeSearchOptions` includes `sourceIds`, `topK`, `filter`, and
the all-important `executionContext` (from the permission-aware tool
execution work — see `actions-as-tools.mdx`). `KnowledgeReindexOptions`
accepts `dryRun` and `limit`; `reindexSource` returns a
`KnowledgeReindexResult` (`indexed`, `discovered`, `skipped`, `purged`,
`ok`, …) — see [Reindex: skip and purge](#reindex-skip-and-purge).

### 3.4 `IKnowledgeAdapter` (implemented by plugins)

```ts
interface IKnowledgeAdapter {
  readonly id: string;
  upsert(docs: KnowledgeDocument[], ctx: AdapterContext): Promise<void>;
  search(query: string, opts: AdapterSearchOptions): Promise<KnowledgeHit[]>;
  delete(documentIds: string[], ctx: AdapterContext): Promise<void>;
  listDocuments?(
    ctx: AdapterContext,
    opts: { cursor?: string; limit: number },
  ): Promise<{ documents: { documentId: string; docHash?: string }[]; nextCursor?: string }>;
  healthCheck?(): Promise<{ ok: boolean; message?: string }>;
}
```

The adapter surface is **deliberately minimal**: no embedding
management, no chunk strategy, no rerank toggles. Those are the
adapter's private concerns. Adapters that need extra knobs expose them
in their plugin options.

Every member past `upsert` / `search` / `delete` is optional (ADR-0161
K8): an adapter that lacks one keeps working, and the service does what it
did before that member existed. `AdapterSearchOptions.organizationIds` is the
caller's organizations; an adapter that reads it ranks only those
organizations' documents, filtering before it ranks — see
[Organization scope](#organization-scope). `listDocuments` lists the documents the
adapter holds for a source, a page of at most `limit` entries at a time, each
with the `docHash` it was stored with; `nextCursor` is absent once the
listing is complete. A document written while a listing runs may be missing
from it — the safe direction, since a missing entry is never purged.

**The contract test suite.** Every adapter package runs the same suite
against its own factory:

```ts
import { runKnowledgeAdapterContract } from '@objectstack/service-knowledge/testing';

runKnowledgeAdapterContract({
  name: 'my-adapter',
  makeAdapter: () => new MyAdapter(/* a fresh, empty store */),
  implements: { listDocuments: true, organizationIds: true },
});
```

It covers upsert / search / delete, `listDocuments` page boundaries and
`docHash` round-trips, the organization filter, and — through a real
`KnowledgeService` — the skip and the purge below, and a search from one
organization under `isolated` and `group`. `implements` declares the optional members, and the suite
checks the declaration against the adapter. `./testing` is a test-only,
ESM-only entry that imports `vitest`; nothing in the runtime entry reaches it.
`knowledge-memory` runs it as the reference implementation.

## 4. Plugin model

Adapters ship as standalone npm packages, registered via the standard
`defineStack({ plugins: [...] })` flow:

```ts
import { KnowledgeServicePlugin } from '@objectstack/service-knowledge';
import { KnowledgeMemoryPlugin } from '@objectstack/knowledge-memory';
import { KnowledgeRagflowPlugin } from '@objectstack/knowledge-ragflow';

defineStack({
  plugins: [
    new KnowledgeServicePlugin(),
    new KnowledgeMemoryPlugin(),                        // dev / test
    new KnowledgeRagflowPlugin({                        // production
      endpoint: process.env.RAGFLOW_URL!,
      apiKey: process.env.RAGFLOW_KEY!,
    }),
  ],
});
```

The plugins are also usable directly against the kernel:
`kernel.use(new KnowledgeServicePlugin())`.

Each plugin:

1. Implements `IKnowledgeAdapter`.
2. In `start()`, looks up `ctx.getService('knowledge')` and calls
   `registerAdapter(id, this)`.
3. Owns its own dependencies (SDK, fetch client, embedder).
4. Owns its own lifecycle / health checks.

Multiple adapters can co-exist; sources pick which one to use via the
`adapter` field.

## 5. Permission-aware retrieval (the unique value-add)

```
caller (user U)
   │
   ▼
search_knowledge tool
   │  ToolExecutionContext { actor: U, … }
   ▼
IKnowledgeService.search(q, { executionContext, sourceIds })
   │
   ├─► per object source: may U reach it? (exposure + field-level rules,
   │       see below) ── a refused source is not searched for U
   │
   ├─► adapter.search(q, …)  ──► returns raw hits with sourceRecordId
   │
   ├─► group hits by underlying object
   │
   ├─► for each group: dataEngine.find(object, { where: { id IN [...] },
   │                                              context: U.ctx })
   │       ── RLS engages, returns only the rows U can see
   │
   ├─► drop hits whose sourceRecordId was filtered out
   │
   └─► return surviving hits to the caller
```

This is the same pattern as the existing permission-aware data tools
(see `actions-as-tools.mdx`).
No matter how aggressive an adapter's retrieval is, the user never
sees a chunk extracted from a record they can't read.

### Organization scope

In a deployment with more than one organization, the adapter ranks only the
caller's organizations' documents (ADR-0161 K8, item 9). Without that, the
best-ranked passages could all belong to another organization, and the
re-read above would empty those places. The filter decides what is ranked;
the re-read still decides what is returned.

- **At assembly.** Under the `group` and `isolated` tenancy postures, a
  document built from a record carries the record's `organization_id` as
  `organizationId`. Under `single`, for `file` / `http` sources and for a
  record with no organization, it carries none.
- **At search.** For each `object` source, the service hands the adapter
  `organizationIds`, the organizations the tenancy wall gives the caller for
  that object: under `isolated` the caller's active organization, under
  `group` every organization the caller holds a membership in. The service
  computes the set from the caller's execution context and the deployment's
  posture. No tool argument or search option supplies it, and
  `search_knowledge` refuses an `organizationIds` argument.
- **No filter** (`organizationIds` absent) under `single`, for the system
  identity, for a `file` / `http` source, and for an object outside the wall
  (tenancy disabled, or no `organization_id` column). The adapter ranks every
  document of the source, as before.
- **An empty set** (`[]`) is a caller with no organization behind a wall, for
  example no active organization under `isolated`. The adapter ranks
  nothing; an empty set never means "no filter".
- **A posture that cannot be read**: a search leaves every `object` source
  unsearched for that call and logs it at `error`. A reindex stops before
  writing anything and says why.

**Documents indexed before this change** carry no `organizationId`. Behind a
wall, a filtered search does not rank them until a complete reindex writes
them again. The organization is part of `docHash`, so the reindex does not
skip them. Under `single` nothing changes: a document without an organization
hashes as before, and the reindex skips it as before.

### Source admission: exposure and field-level rules

A passage is built at index time, under a system context, from every
`contentFields` member of its source, the object's display field (the
title) and the source's `metadataFields`. A row re-check alone would therefore serve a caller the text
of a field a field-level rule hides from them. So before an `object` source is
searched for a non-system caller, the service asks, once per object per search:

- **Disabled package** — an object whose owning package is disabled is not
  searched.
- **API exposure** — the spec's one exposure decision for the `search`
  operation, the one the cross-object search asks: `enable.apiEnabled: false`,
  or an `enable.apiMethods` whitelist that does not grant `search` (granting
  `list` does), keeps the object's sources out of the search.
- **System objects** — a `sys_*` object is searched only when it declares
  `enable.aiReadable: true` (the AI read tools' posture).
- **Field-level rules** — every field the source serves (each `contentFields`
  member, `'*'` meaning every field the object declares except `id`; each `metadataFields`
  member; the display field the title is read from), less the
  credential-class and `internal: true` fields an
  index never carries, must be one the caller may **query**, per the `security`
  service's `getQueryableFields`. Without that answer: its `getReadableFields`
  less every field declaring a `maskingRule`; with no `security` service at
  all: every field except those declaring a `maskingRule`. Queryable, not
  merely readable, because a passage carries the unmasked value.

The answer is per **source**, not per field: when one served field is hidden
from the caller, that source is not searched for them at all — its passages
mix the hidden field's text into one unit that cannot be partially withheld.
To keep a source searchable for restricted callers, declare its
`contentFields` / `metadataFields` from fields every intended reader may query,
and put sensitive fields in a separate source. Every gate fails closed: a
lookup that throws — the `security` service lookup included, unless the kernel
answers that no `security` service is registered — or a `security` service
that answers neither field question, keeps the source out of that caller's
search. The system context bypasses these gates as it bypasses the row
re-check. A caller with no execution context, or a service with no data engine
bound, is searched no `object` source at all; an `object` source's hit with no
`sourceRecordId` cannot be re-checked and is dropped; and the service drops a
hit whose reported `sourceId` names another source than the one searched. That
check sees only the `sourceId` an adapter reports: an adapter that labels
another source's passage with the searched source's id is not caught by it, so
two sources must not share one adapter-side store. A restricted caller's empty
answer is this narrowing, not a missing index.

For `file` and `http` sources (no underlying ObjectQL record), the
adapter is responsible for honouring an opaque `permissions` field on
each document. Sources that need fine-grained ACLs should be declared
with a `permissions` mapping function at index time.

## 6. Sync model

For `object` sources, `KnowledgeService` subscribes to the ObjectQL engine's
`data.record.created`, `data.record.updated`, `data.record.restored` and
`data.record.deleted` events. A bare `record.*` event is not part of the
vocabulary: no producer emits one, and the subscription ignores it.

A source's `where` decides which rows it indexes on every path — the event
sync as well as `reindexSource`. For a created, updated or restored row, with a
data engine bound, each source re-reads the row under the system context:
`find(object, { where: { $and: [where, { id }] }, limit: 1 })` (just `{ id }`
when the source has no `where`).

- **A row comes back** — the document is built from the re-read row, not from
  the event's `after`, so a write result that omits a field (a projected
  result, a formula the write did not return) cannot leave the document
  short. The same field rules as a reindex apply: the fields the source lists
  and the object's display field as the title, never a credential-class or
  `internal` field.
- **No row comes back** — the row does not match (a draft, or a row that
  stopped matching), and its document is deleted. Deleting an absent document
  changes nothing.
- **A restored row** (a recycle-bin restore) takes the same path, so it
  re-enters the index only if it matches.
- **No data engine bound** — nothing can be re-read: a source without `where`
  builds the document from the event's `after`, and a source with `where` is
  not synced, which the service logs once per source as a warning.

A delete removes the document named by the event's required `recordId`. Syncs
of one document run one after another in the process, so two events for the
same row cannot interleave: each re-reads after the previous one finished, and
the last leaves the index agreeing with the database. Because the sync is
inline, a write's sync can wait behind an earlier in-flight sync of the same
document (on a single-connection pool, up to the pool's acquire timeout); the
index still ends consistent.

**When the sync runs.** The engine publishes `data.record.created` and
`data.record.updated` from inside the write, after its `after*` hooks — before
any unit of work around the write commits (the write's own unit, opened when a
metadata hook can abort it, or a caller's `engine.transaction(…)`). The
in-process realtime service awaits each subscriber, so the re-read runs inside
the same open transaction and sees the row the write just made. If that unit
then rolls back, the index is wrong in one of two ways:

- **The uncommitted row matched** — the document stays built from a row that
  never committed.
- **The uncommitted row did not match** — the document was deleted, so the
  committed row, which may still match, is missing from the index.

The row's next event or a `reindexSource` repairs a row that still exists. A
document built from an **insert** that rolled back has no row left to repair it
from; it stays until a complete reindex purges it (below).

`data.record.restored` is
published after the restore's own unit has committed.

- **MVP (Phase 1):** synchronous, inline with the originating mutation.
  Fast for low-volume dev / demo. Indexing failures are logged but do
  not block the originating write.
- **Phase 2:** async via `service-queue` for batching, retries, and
  back-pressure.

<Callout type="warn">
  **A predicate write leaves the index stale.** A `multi: true` update/delete
  reaches `updateMany` / `deleteMany`, which report only an affected row count,
  so it publishes the aggregate `data.records.updated` / `data.records.deleted`
  ([#4639](https://github.com/objectstack-ai/objectstack/issues/4639)) rather
  than per-record events. A knowledge index is a per-record projection and
  `matched: 40` names no record, so there is no upsert or delete to derive —
  the service logs a warning naming the object and count instead of failing
  silently. A complete `reindexSource` refreshes the documents of rows that
  still exist and match, and — over an adapter that implements
  `listDocuments` — purges those of deleted rows and of rows that stopped
  matching. Over an adapter that does not, they stay in the index.
</Callout>

### Reindex: skip and purge

A `reindexSource` of an `object` source over an adapter that implements
`listDocuments` first lists what the adapter holds for the source (document
id → stored `docHash`), then walks the object's rows page by page:

- **Skip.** A row whose document's computed `docHash` equals the listed one is
  not written again; the result counts it in `skipped`. Every other document
  is written (`indexed`). A listed entry without a `docHash` reads as changed.
- **Purge.** After a **complete** walk — no `limit`, no `dryRun`, no failed
  page — every document listed before the walk that the walk did not see is a
  candidate. Each candidate is confirmed by the same re-read the event sync
  makes (the source's `where` AND the record id, under the system context) and
  deleted only when that finds no row. A row created or restored during the
  walk keeps its document: if it was listed, the re-read finds it; if it was
  not, it was never a candidate. The purge of a document waits for any
  in-flight event sync of the same document. `purged` counts the deletions.
- **Known limit: numeric record ids.** The purge reads the record id back from
  the document id as text and re-reads by that text. On driver-mongodb and
  driver-memory, which do not equate `'5'` with `5`, a row stored under a
  caller-supplied numeric id is not found by that re-read; if such a row was
  restored (or came back into `where`) after the walk read past it, its
  document is deleted. The row itself is untouched, and its document returns at
  the row's next event or the next complete reindex. Platform-minted ids are
  text on every driver, so this needs a caller-supplied numeric id.
- **`purged: null`** means no purge ran: a walk with a `limit` or a `dryRun`,
  a failed walk, a source with `refresh.onRecordChange: false` (an external
  indexer owns its index), or an adapter without `listDocuments` — which also
  skips nothing, the walk otherwise unchanged. A listing that fails skips and
  purges nothing either, and the result's `message` says why.
- A listed document whose id is not one the source derives from a record
  (`<sourceId>:<recordId>`) is never purged, since no row can confirm it; the
  result's `message` counts such documents.

A re-read or delete that fails stops the purge — a re-read that answers no
list of rows counts as failed, never as "no row" — and the result is
`ok: false`, `purged` counts the deletions made before it, and the `message`
names the document. A walk page that answers no list of rows stops the walk
the same way, with `purged: null`, rather than ending it as if the source were
empty. The event sync shares that re-read: when it answers no list of rows, the
sync leaves the document in place and logs a warning, rather than deleting it.

### Retention deletes are covered by a reap guard

The platform's own predicate delete — `LifecycleService` reaping rows past
their retention window — is the one bulk path that *is* handled, and it is
handled at the source rather than after the fact
([#4672](https://github.com/objectstack-ai/objectstack/issues/4672)).

For every object an `object` source projects, the plugin registers an ADR-0057
**reap guard** with the lifecycle service. The sweep hands the guard the
candidate rows before deleting them; the guard deletes each row's document and
returns the ids it confirms. Rows it does not confirm stay put.

- **Failure direction.** If `adapter.delete` fails, the row is *kept* and
  retried on the next sweep. A row may outlive its index entry; an index entry
  must never outlive its row, because an orphan still consumes a `topK` slot
  ahead of the permission filter and is read straight through by an `isSystem`
  caller.
- **Composition.** Guards from different packages compose by intersection, so
  this one cannot displace another registrar's cleanup (or be displaced by it).
- **Batching** is the sweep's: 500 rows per batch, 20 batches per sweep, the
  backlog draining across sweeps.
- **Opt-out.** `refresh.onRecordChange: false` on a source — or
  `enableEventSync: false` on the plugin — turns off inline index sync in both
  directions, event subscription and reap-time de-index alike. An index an
  external indexer owns is never a reason to hold up another package's
  retention.

Application-level predicate writes are not de-indexed as they happen. Their
stale documents are removed by the next complete `reindexSource`, over an
adapter that implements `listDocuments` ([Reindex: skip and
purge](#reindex-skip-and-purge)); nothing runs that reindex on a schedule yet.

`file` / `http` sources rely on explicit `reindexSource` calls
(typically triggered by a cron job, a Console button, or a webhook).

## 7. MVP (Phase 1) scope

Phase 1 ships the protocol, the orchestrator, two adapters, and the AI
tool wiring. It is **not** production-grade — it is "production-shaped":
the surface is stable, the unique value-add (permission-aware
retrieval) works end-to-end, and a real adapter (`ragflow`) is wired
up.

| Component | In Phase 1 | Notes |
|-----------|-----------:|-------|
| `KnowledgeSourceSchema` | ✅ | object / file / http kinds |
| `KnowledgeDocument` / `Chunk` / `Hit` | ✅ | Canonical shapes |
| `IKnowledgeService` contract | ✅ | search / index / delete / reindex |
| `IKnowledgeAdapter` contract | ✅ | upsert / search / delete / healthCheck; optional `listDocuments` with a contract test suite (`@objectstack/service-knowledge/testing`) |
| `service-knowledge` orchestrator | ✅ | Adapter routing, RLS wrapper, sync |

| Event-driven sync for `object` sources | ✅ (sync) | MVP synchronous; queue in Phase 2 |
| Console source-management UI | ⏳ Phase 2 |  |

| `knowledge-pgvector` | ⏳ Phase 3 |  |

### 7.1 Non-goals for Phase 1

- Reranker hooks, hybrid retrieval toggles, MMR — adapter-private.
- Field-level masking inside a passage. A source serving a field the caller
  may not query is not searched for that caller at all (§5, source
  admission); a passage is never re-projected or redacted per caller.
- Cost / quota enforcement — Phase 2.
- Multi-tenant index isolation — defer to adapter capability matrix.

## 8. Compatibility with existing `Embedding` primitives

`packages/spec/src/ai/embedding.zod.ts` already defines
`EmbeddingModelSchema` and `VectorStoreSchema`. Those primitives
describe *configuration*; the Knowledge Protocol describes *behaviour*.

Adapters may consume `EmbeddingModel` / `VectorStore` references from a
`KnowledgeSource.embedding` field (when supplied), but they are free to
ignore them when the underlying backend manages embeddings
internally (RAGFlow, Dify, Vectara).

## 9. Open questions

- **Where does chunk-level ACL live?** The framework checks row-level
  ACLs by re-querying via `dataEngine.find`, and field-level rules at
  source granularity (§5): a source serving a field the caller may not
  query is not searched for them. Finer grain — serving such a caller a
  passage with the hidden field's text removed — would require either
  (a) indexing one passage per field-visibility class or (b) standardising
  a `redact` step. Deferred.
- **Multiple adapters per source.** Useful for mirroring (e.g. write
  to RAGFlow and pgvector simultaneously) but adds significant
  complexity. Not in Phase 1.
- **Embedding cost attribution.** Belongs in `service-analytics`. The
  Knowledge Protocol simply emits typed events.
