Control visibility and editability of specific fields.

## Field Permissions in Permission Sets

Field permissions are keyed `<object>.<field>` and use `readable` / `editable`,
plus an optional `when` — a row condition on the edit vote (below):

```typescript
fields: {
  // Read-only: visible but not editable
  'account.annual_revenue': { readable: true, editable: false },
  'account.description': { readable: true, editable: true },
  // Hidden: not visible at all
  'account.ssn': { readable: false, editable: false },
  'opportunity.amount': { readable: true, editable: true },
  'opportunity.probability': { readable: true, editable: false },
}
```

## Row-conditioned edit locks (`when`)

An entry may carry `when`: a row condition in the same canonical CEL as an
RLS `using` predicate (a field of the object compared with a literal or a
`current_user.*` value; `==`, `!=`, `<`, `<=`, `>`, `>=`, `in`, combined with
`&&` / `||`). The entry then votes **only on the rows the condition matches**
and is absent on every other row, as if the set had not declared the field:

```typescript
fields: {
  // Locked from approval onward; a draft is still editable.
  'opportunity.amount': { readable: true, editable: false, when: "status in ['approved', 'closed']" },
  // Editable on the caller's own rows only.
  'task.estimate': { readable: true, editable: true, when: 'assigned_to == current_user.id' },
}
```

- **Edit vote only.** Reads are judged row-blind, so `readable: false`
  beside a `when` is refused at parse time; keep `readable: true` (the
  default) on a row-conditioned entry.
- **Which row.** The write gate judges the **stored** row before an update
  (a lock on `status in [...]` holds on an approved row even when the same
  write moves `status` back), and each **incoming** row of an insert, as the
  caller sent it. The condition is evaluated in process against the row —
  never rewritten into the query.
- **When no row can be judged** — a predicate (bulk) update with no row
  address, a stored row the caller cannot read, a condition that does not
  resolve for the request — the entry is applied as its **lock**: no edit
  grant on that write, and a WARN line says why.
- **Readers that hold no row** (`/auth/me/permissions`, the object-wide
  writable-field projections, `os explain`) report a row-conditioned entry
  as its lock, so a client never advertises an edit the gate refuses.
  `os explain` names each such entry as a row-conditioned lock in its `fls`
  layer.
- **The record-scoped projection holds the row.**
  `GET /api/v1/data/{object}/{id}/field-access` (`client.data.fieldAccess`)
  answers the fields the caller may read and the fields it may write on
  **that** record, and its `editable` list is the write gate's own verdict on
  an update of the stored row. So a lock that applies from a stage onward
  disables the field only on the rows its condition names — this is the
  answer a record's edit form and the record page's in-place edit read. A
  list view's inline edit locks a whole column, which cannot split per row,
  so it keeps the row-blind answer. A row that is absent or that the caller
  cannot read answers the record read's `404`. The answer is field-level
  only: the object grant and the record's row-level write scope (sharing,
  row-level security, ownership) are not part of it, so on a row the caller
  may read but not write it still lists fields as editable, and the update
  is refused as a whole.
- **Union without deny is unchanged.** A matched conditioned lock is still
  out-voted by another set's unconditioned `editable: true`; an entry
  without `when` votes on every row, as before (ADR-0066 ⑧, note of
  2026-10-26).
- **Validated at authoring.** `objectstack validate` judges `when` like an
  RLS predicate (`rls-predicate-*` findings on `permissions[].fields[].when`):
  the fields it names must exist on the entry's object, no cross-object
  reach, no unresolvable `current_user.*` variable.
- **In Studio.** The permission-set form offers the condition on each field
  row under **When (edit)**, in the same CEL editor as the row-level security
  clauses, linted the same way; a condition the publish gate would refuse
  holds the save. Switching **Read** off clears the condition, and the
  **Read-only all** / **Write all** shortcuts keep it. A field row with no
  rule shows the object's own Read / Edit in grey, marked as following the
  object; a click or a shortcut writes a rule only for the boxes it changes,
  and **Clear** returns the visible rows to the object grant.

For an administrator's walk-through (the editor path, the matching metadata,
and when a validation rule is the better tool), see the recipe
[Lock fields for a position once a record reaches a stage](/docs/permissions/access-recipes#data-lock-fields-for-a-position-once-a-record-reaches-a-stage).

## Hidden vs. Read-Only

```typescript
// Hidden: Field not visible at all
{ readable: false, editable: false }

// Read-Only: Field visible but not editable
{ readable: true, editable: false }

// Editable: Field visible and editable
{ readable: true, editable: true }
```

## Server-side enforcement of declared rules

The client-side ObjectForm / inline grid hides non-editable fields from
the UI — but that is a **UX layer only**. The SecurityPlugin middleware
enforces field-level write rules on the server, regardless of how the
request arrived (REST, SDK, raw ObjectQL call).

**On read** — `find` / `findOne` results have non-readable fields
stripped from every record before the response leaves the engine.

**On write** — `insert` / `update` requests are checked **before** the
operation reaches the driver. If the payload contains any field the
caller is not permitted to edit, the engine throws
`PermissionDeniedError` (mapped to HTTP 403) with the offending field
names in `details.forbiddenFields`:

```json
{
  "name": "PermissionDeniedError",
  "code": "PERMISSION_DENIED",
  "statusCode": 403,
  "message": "[Security] Field write denied: not permitted to edit [salary, ssn] on 'employee'",
  "details": {
    "operation": "insert",
    "object": "employee",
    "forbiddenFields": ["salary", "ssn"]
  }
}
```

**Why throw instead of silently stripping?** Silent strip hides the
security boundary from honest clients (their update "doesn't save" and
they cannot tell why) AND gives a probing client no signal that the
field exists. Throwing makes the boundary observable in both directions
— legitimate UIs get an actionable error to fix; probing clients learn
nothing they could not already infer.

**Default-visible (block-list) semantics.** Fields without an explicit
rule pass through untouched — readable *and* writable. Permission sets
only constrain fields they explicitly enumerate, and field grants union
most-permissively across a user's sets (one set's `readable: true`
out-votes another set's `false`). Until a subtractive muting layer lands
(ADR-0066 ⑧), a `{ readable: false }` rule masks the field only as long
as **no other set the user holds** declares it `readable: true` — so
protect sensitive fields by granting them only in the sets that need
them, and treat a sensitive field on a broadly-granted object as a
review smell — see the
[FLS posture warning](/docs/permissions/authorization#combination-semantics-the-fixed-order).
Declared rules themselves are enforced fail-closed: a masked field is
stripped on read and a write to a non-editable field throws.

**Bulk inserts.** Arrays are checked row-by-row; a single offending
field in any row rejects the whole batch atomically.

**System operations.** `ExecutionContext { isSystem: true }` bypasses
the check entirely — used for migrations, seed loading, and audit log
writes.
