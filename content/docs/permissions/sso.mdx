ObjectStack open source ships two built-in social sign-in implementations, both wired by `os serve` from deployment env vars:

- **Google OAuth**: configure in Setup → Authentication, or from
  `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` deployment env vars
- **GitHub OAuth**: configure from `GITHUB_CLIENT_ID` and
  `GITHUB_CLIENT_SECRET` deployment env vars

Additional providers should be contributed by product or enterprise packages through
the `auth:configure` hook. Those packages can add better-auth `socialProviders`
or OIDC/generic OAuth providers without forking `@objectstack/plugin-auth`.

The Console login and registration pages automatically render **Continue with ...**
buttons for every enabled provider returned by `/api/v1/auth/config`.

---

## Social Providers

### Google

1. Go to [Google Cloud Console](https://console.cloud.google.com/) → **APIs & Services** → **Credentials**.
2. Click **Create Credentials** → **OAuth 2.0 Client ID** → **Web application**.
3. Add an **Authorized redirect URI**:
   ```
   https://<your-domain>/api/v1/auth/callback/google
   ```
   For local development: `http://localhost:3000/api/v1/auth/callback/google`
4. Copy the **Client ID** and **Client Secret**.

Then either save the values in **Setup → Authentication → Social sign-in** or
provide them as deployment environment variables:

```bash
GOOGLE_CLIENT_ID=your-google-client-id
GOOGLE_CLIENT_SECRET=your-google-client-secret

# Optional settings env override. UI settings are lower precedence than env.
# OS_AUTH_GOOGLE_ENABLED=false
```

### GitHub

1. Go to [GitHub Developer Settings](https://github.com/settings/developers) → **OAuth Apps** → **New OAuth App**.
2. Set **Authorization callback URL**:
   ```
   https://<your-domain>/api/v1/auth/callback/github
   ```
3. Copy the **Client ID** and generate a **Client Secret**.

Provide them as deployment environment variables:

```bash
GITHUB_CLIENT_ID=your-github-client-id
GITHUB_CLIENT_SECRET=your-github-client-secret
```

## Extension Packages

The providers below are examples for enterprise or product packages, not built-in
open-source settings. A package can register them by listening to `auth:configure`
and mutating the draft auth config.

The env-var names shown below (e.g. `MICROSOFT_CLIENT_ID`, `APPLE_CLIENT_ID`) are
illustrative for an extension package's own reader code — unlike `GOOGLE_*` and
`GITHUB_*`, the framework does **not** read them out of the box, so an extension
must wire them in its `auth:configure` handler.

### Microsoft (Azure AD / Entra ID)

1. Go to [Azure Portal](https://portal.azure.com/) → **Azure Active Directory** → **App registrations** → **New registration**.
2. Add a redirect URI (Web):
   ```
   https://<your-domain>/api/v1/auth/callback/microsoft
   ```
3. Under **Certificates & secrets**, create a new client secret.

```bash
MICROSOFT_CLIENT_ID=your-azure-app-client-id
MICROSOFT_CLIENT_SECRET=your-azure-client-secret

# Optional: restrict to a single tenant (default: "common" — all Microsoft accounts)
# MICROSOFT_TENANT_ID=your-tenant-id
```

### Apple

1. Go to [Apple Developer Console](https://developer.apple.com/) → **Certificates, IDs & Profiles** → **Identifiers** → register a **Services ID**.
2. Enable **Sign In with Apple** and configure the redirect URL:
   ```
   https://<your-domain>/api/v1/auth/callback/apple
   ```
3. Generate a **private key** under **Keys**.

```bash
APPLE_CLIENT_ID=your-apple-services-id
APPLE_CLIENT_SECRET=your-apple-private-key-jwt
```

> Apple requires the client secret to be a signed JWT derived from the private key. See [better-auth Apple docs](https://www.better-auth.com/docs/authentication/apple) for details.

## Enterprise SSO (OIDC)

Admin-managed **OIDC SSO ships in the open framework**: `@objectstack/plugin-auth`
registers external IdPs through `@better-auth/sso`, and admins add them **without
code** from **Setup → SSO Providers** (see the ADR-0069 note below). The
`oidcProviders` config shown here is the in-process path for framework or product
packages that prefer wiring providers in code, or contributing them through
`auth:configure`.

> **Admin-managed external IdP (ADR-0069).** Recent releases add a
> per-environment external-IdP path built on `@better-auth/sso` and surface an
> `sso` flag in the public `/auth/config` (`features.sso`) so a client can show
> an enterprise-login button when SSO is configured. Admins register providers
> **without code** from **Setup → SSO Providers** — both **OIDC** (Okta, Entra,
> Auth0, Keycloak, …) and **SAML 2.0** (see [SAML 2.0](#enterprise-sso-saml-20)
> below). The `oidcProviders` extension shown here remains the in-process path
> for framework/enterprise packages that prefer wiring providers in code.

**Setup → SSO Providers → Register Provider** posts to the env-side bridge at
`POST /api/v1/auth/admin/sso/register`, the OIDC counterpart of the SAML bridge
[below](#enterprise-sso-saml-20). It takes the flat form fields of the
[OIDC provider fields](#oidc-provider-fields) table, reshapes them for
`@better-auth/sso`, and is gated on a **platform admin** (ADR-0068 D4) before it
delegates — an organization owner or admin is not sufficient, because registering
an identity provider decides how the whole environment authenticates.

<Callout type="info">
This is an ObjectStack mount, distinct from `@better-auth/sso`'s own
`POST /api/v1/auth/sso/register`. The bridge exists so the no-code Setup form can
post flat fields; both doors apply the platform-admin rule.
</Callout>

### Register Microsoft Entra ID

Register an Entra ID application from **Setup → SSO Providers → Register
Provider**, or through `POST /api/v1/auth/sso/register`, with the issuer
`https://login.microsoftonline.com/<tenant-id>/v2.0`. No trusted-origins
configuration is needed.

**Discovery.** Entra ID's discovery document names its `userinfo_endpoint` on
`https://graph.microsoft.com`, a host other than the issuer's. The server keeps a
built-in table of such companion origins for well-known identity providers, and
trusts `https://graph.microsoft.com` only while it validates the discovery
document of a registration whose issuer is an `https://login.microsoftonline.com`
URL. It is not added to the trusted origins that the CSRF check reads, and no
other request sees it. Sovereign-cloud Entra hosts are not in the table: name
their userinfo endpoint explicitly, as below.

**Any other identity provider** whose discovery document names an endpoint on a
foreign host is refused **400 `discovery_untrusted_origin`**. The message names
the endpoint and the registration member that names it explicitly, for example
`"userInfoEndpoint": "https://profile.example.com/userinfo"`. A host is never
trusted only because a discovery document names it. Pass the endpoint as
`oidcConfig.userInfoEndpoint` (or as `userInfoEndpoint` on the Register SSO Provider
bridge, `POST /api/v1/auth/admin/sso/register`, which the **Userinfo URL** field of
**Setup → SSO Providers → Register SSO Provider** fills), and the
registration trusts it.

**Claims.** Microsoft Graph's userinfo answer carries `sub`, `name`, `email` and
`picture`, but no `groups`, `preferred_username` or `upn`. Two things follow:

- **Groups come from the verified ID token.** When the userinfo answer does not
  carry the provider's groups claim (`mapping.extraFields.groups`), the groups
  are read from the ID token the server has already verified. Where both carry
  the claim, the userinfo answer wins. See
  [Grant permission sets from IdP groups](#grant-permission-sets-from-idp-groups).
- **A user without a mailbox needs an email mapping.** Entra ID sends no `email`
  claim for a user with no mailbox, and such a sign-in is refused
  `email_claim_missing` (see [Why an OIDC sign-in was refused](#why-an-oidc-sign-in-was-refused)).
  Set **Map: Email claim** on the register form, or the email member with
  **Edit Attribute Mapping** on an existing provider, to `preferred_username`
  (or `upn`), and turn on
  **Read Claims From the ID Token Only** (`skipUserInfo`, see
  [Per-provider sign-in options](#per-provider-sign-in-options)), because while
  userinfo is called the mapping reads the userinfo answer, which has neither.
  The server never makes up an email address from another claim on its own.

### OIDC provider fields

| Field | Required | Description |
|---|---|---|
| `providerId` | ✅ | Unique identifier used internally (e.g. `okta`, `azure-ad`) |
| `name` | — | Display name shown on the button (defaults to `providerId`) |
| `discoveryUrl` | ✅* | OIDC discovery URL — auto-fetches all endpoints |
| `authorizationUrl` | ✅* | OAuth2 authorization endpoint (if no `discoveryUrl`) |
| `tokenUrl` | ✅* | OAuth2 token endpoint (if no `discoveryUrl`) |
| `userInfoUrl` | — | OAuth2 userinfo endpoint |
| `issuer` | — | Expected issuer for token validation |
| `clientId` | ✅ | OAuth2 client ID |
| `clientSecret` | ✅ | OAuth2 client secret |
| `scopes` | — | Requested scopes (default: `openid email profile`) |
| `pkce` | — | Enable PKCE — recommended for public clients |

*Either `discoveryUrl` or `authorizationUrl` + `tokenUrl` must be provided.

### Domain verification (opt-in)

A provider can claim an email **domain**, so that anyone signing in with an
address at that domain is routed to it. Proving the claim is opt-in per
environment (ADR-0135 D6) and off by default:

```bash
# Off by default. Turn on to require a DNS proof before a domain claim counts.
OS_SSO_DOMAIN_VERIFICATION=true
```

With it on, **Setup → SSO Providers** exposes a two-step flow, one route per
step. Both are platform-admin gated (ADR-0068 D4) and both take the provider the
domain is being claimed for:

1. `POST /api/v1/auth/admin/sso/request-domain-verification` — returns a DNS
   **TXT** record to publish on the domain. Copy it into your DNS zone.
2. `POST /api/v1/auth/admin/sso/verify-domain` — call once the record has
   propagated. It re-checks DNS and marks the domain verified, or reports why it
   could not.

```typescript
// Step 1 — ask for the TXT record to publish.
// Body: { providerId, domain? }. `domain` only shapes the record NAME shown back
// to you; omit it and you get the bare label to place on the zone yourself.
const req = await fetch('http://localhost:3000/api/v1/auth/admin/sso/request-domain-verification', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  credentials: 'include',
  body: JSON.stringify({ providerId: 'okta', domain: 'acme.example' })
});
// → { success: true, data: { providerId, domain, token,
//                            dnsRecordType: 'TXT', dnsRecordName, dnsRecordValue } }

// …publish dnsRecordName / dnsRecordValue, wait for DNS to propagate, then:

// Step 2 — verify the claim. Body: { providerId }.
const done = await fetch('http://localhost:3000/api/v1/auth/admin/sso/verify-domain', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  credentials: 'include',
  body: JSON.stringify({ providerId: 'okta' })
});
// → { success: true, data: { providerId, verified: true, message } }
```

Both take `providerId` and refuse with **400 `INVALID_REQUEST`** when it is
missing. Step 2 reports `NO_PENDING_VERIFICATION` if you call it before step 1,
and `DOMAIN_VERIFICATION_FAILED` when the TXT record is not visible yet — retry
after DNS propagates.

<Callout type="info">
**The mounts are unconditional; the switch controls the endpoint behind them.**
Both routes exist whether or not `OS_SSO_DOMAIN_VERIFICATION` is set — and with
it unset there is no endpoint behind them, so both steps answer **400
`DOMAIN_VERIFICATION_DISABLED`**. With it on, either step answers an unknown
`providerId` with **404 `RESOURCE_NOT_FOUND`**; step 2's `NO_PENDING_VERIFICATION`
is a 404 too, so match on the code rather than the status. Either way an anonymous
caller gets **401 `UNAUTHENTICATED`** and a signed-in non-platform-admin **403
`PERMISSION_DENIED`** — identity is answered before capability, so a stranger
cannot use these routes to probe which features an environment has enabled.
</Callout>

What verification decides, with it on:

- **A provider signs nobody in until its domain is verified.** Step 2 proves
  every domain the provider lists, and one verified flag covers the whole list.
  Editing a provider's domain list clears the flag until every listed domain is
  proven again.
- **A provider creates an account only for an email address at a domain it has
  proven.** The address's domain must equal one of the provider's listed,
  verified domains. A subdomain counts only when it is itself listed and
  verified, and a parent never counts for a listed subdomain. A listed entry
  counts only for the host the provider proved, so write each entry as a bare
  host name (`acme.com`, not `https://acme.com` and not `acme.com:443`): an
  entry written any other way proves nothing. Case, and the Unicode and
  punycode forms of an internationalised name, are one domain; an address
  written in any other spelling of a domain (a trailing dot, full-width
  letters) is refused. Any other new account is refused with
  `error=EMAIL_DOMAIN_NOT_ALLOWED`, and nothing is created. No audience
  posture, invitation, first-user carve-out or `allowJit` setting relaxes this.
- **Accounts that already exist are not re-checked.** A person who already has
  an account signs in as before.

So if your people first sign in with addresses at a subdomain or at another
domain, list each such domain on the provider as a bare host name and verify it.

### Why an OIDC sign-in was refused

When the identity provider's ID token is not accepted, the callback redirects to
your `errorCallbackURL` (or `callbackURL`) with `error=invalid_provider`, and
`error_description` names the cause. The server also writes one `warn` log line
with the `providerId`, `protocol: 'oidc'` and the same `cause`. Neither carries
any token content, and the answer does not depend on whether the account exists.

| `error_description` | What to check |
| :--- | :--- |
| `id_token_expired` | The token's `exp` is in the past. Check the clocks of this server and the IdP. |
| `id_token_not_yet_valid` | The token's `nbf` is in the future. Check the clocks of this server and the IdP. |
| `id_token_audience_mismatch` | The token's `aud` is not this provider's `clientId`. Check the client ID registered here against the IdP application. |
| `id_token_issuer_mismatch` | The token's `iss` is not this provider's `issuer`. Check the issuer URL, including any trailing path or slash. |
| `id_token_signing_key_unknown` | No key in the IdP's JWKS matches the token's key ID, usually after the IdP rotated or retired its signing key. Check the `jwksEndpoint`. |
| `id_token_signature_invalid` | The JWKS key does not verify the token's signature. Check that the `jwksEndpoint` belongs to the same IdP as the `issuer`. |
| `token_not_verified` | Any other refusal of the ID token. The server log carries the detail. |
| `email_claim_missing` | The ID token was accepted, but the claim the provider maps to the email (`mapping.email`, `email` by default) is missing. The warn line names the claim and the mapping key. For a Microsoft Entra ID user without a mailbox, map `preferred_username` or `upn` and turn on `skipUserInfo`. |

The ID-token causes are exported as `SSO_OIDC_REFUSAL_CAUSES` from
`@objectstack/plugin-auth`, and `email_claim_missing` as
`SSO_OIDC_EMAIL_CLAIM_MISSING`.
SAML refusals name theirs too: see [Why a SAML sign-in was refused](#why-a-saml-sign-in-was-refused).

## Enterprise SSO (SAML 2.0)

SAML 2.0 is provided natively by `@better-auth/sso` (the same package behind the
OIDC path) — **no custom plugin or extension is needed**. Admins register a SAML
IdP from **Setup → SSO Providers → Register SAML Provider**, which posts to the
env-side bridge at `POST /api/v1/auth/admin/sso/register-saml`.

### Register a SAML provider

Fill in the IdP details collected by the **Register SAML Provider** action:

| Field | Required | Description |
|---|---|---|
| `providerId` | ✅ | Stable identifier, e.g. `acme-saml`. |
| `issuer` | ✅ | The IdP's SAML **EntityID** (issuer), e.g. `https://saml.acme.com/entityid`. |
| `domain` | ✅ | Users with this email domain are routed to this IdP, e.g. `acme.com`. |
| `entryPoint` | ✅ | The IdP's SAML single sign-on (redirect) URL that receives the `SAMLRequest`. |
| `cert` | ✅ | The IdP's X.509 signing certificate (PEM body) — used to verify assertion signatures. |
| `identifierFormat` | — | Requested SAML NameID format (defaults to the IdP's configured format), e.g. `urn:oasis:names:tc:SAML:1.1:nameid-format:emailAddress`. |
| `mapEmail` | — | Assertion attribute the user's email is read from. Defaults to `email`, then the NameID. |
| `mapFirstName` | — | Assertion attribute the user's first name is read from. Defaults to `givenName`. |
| `mapLastName` | — | Assertion attribute the user's last name is read from. Defaults to `surname`. |
| `mapName` | — | Assertion attribute the user's full name is read from when the first and last name are absent. Defaults to `displayName`, then the NameID. |
| `mapGroups` | — | Assertion attribute that carries the user's groups (see [Grant permission sets from IdP groups](#grant-permission-sets-from-idp-groups)). |

On success the response returns the two **Service Provider (SP)** URLs you
configure on the IdP side:

```json
{
  "success": true,
  "data": { "providerId": "acme-saml" },
  "acsUrl": "https://<your-domain>/api/v1/auth/sso/saml2/sp/acs/acme-saml",
  "spMetadataUrl": "https://<your-domain>/api/v1/auth/sso/saml2/sp/metadata?providerId=acme-saml"
}
```

- **ACS (Assertion Consumer Service) URL** — register this as the SP ACS / reply
  URL on the IdP.
- **SP metadata URL** — serves the SP `EntityDescriptor`/`SPSSODescriptor` XML
  (many IdPs can import it directly to auto-configure the SP).

### SAML sign-in flow

1. User enters their work email (or clicks the enterprise-login button).
2. Client calls `POST /api/v1/auth/sign-in/sso` with `{ email, callbackURL }`
   (and optionally `errorCallbackURL`).
3. The email **domain** is matched to the registered provider; the response is a
   redirect to the IdP's `entryPoint` carrying a signed `SAMLRequest`.
4. The IdP authenticates the user and POSTs a SAML assertion back to the SP ACS
   URL; `@better-auth/sso` (samlify) validates the signature/timestamp, then
   creates a session and redirects to `callbackURL`.
5. A refused sign-in redirects to `errorCallbackURL`, or to the platform's
   sign-in page when none was given, with `error=` naming the refusal: for
   example `account_not_linked` when the email belongs to an existing account
   this provider is not linked to. It never lands on `callbackURL`, as with OIDC.

> Signature, timestamp, and replay validation are handled by `@better-auth/sso`
> (samlify). You only supply the IdP's signing certificate at registration time.

### Map the user's email and name

A SAML sign-in reads the user's email and name from assertion attributes. With
nothing mapped, the email is the `email` attribute (else the NameID) and the name
is `givenName` + `surname`, else `displayName`, else the NameID. Okta and Entra ID
use other attribute names, so their users are named after their NameID until the
provider maps them:

| Member | Default | Okta (common) | Entra ID |
| :--- | :--- | :--- | :--- |
| Email | `email` | `email` | `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress` |
| First name | `givenName` | — | `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/givenname` |
| Last name | `surname` | — | `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/surname` |
| Display name | `displayName` | `name` | `http://schemas.microsoft.com/identity/claims/displayname` |

Okta sends the attributes its application's attribute statements name, so check
those statements for the exact names. Map them on the **Register SAML Provider**
form, or on an existing provider:

- **Show Attribute Mapping** shows the attributes (SAML) or claims (OIDC) the
  provider reads now; an empty member uses the default.
- **Edit Attribute Mapping** changes the members you fill in. A member you leave
  untouched keeps its value, and a member you clear goes back to the default.
  The groups claim and every other member of the mapping are kept as stored.
  An OIDC provider maps `email` and `name` only (its default claims are `email`
  and `name`).

Both run on platform-admin standing, through `POST
/api/v1/auth/admin/sso/get-attribute-mapping` and `POST
/api/v1/auth/admin/sso/set-attribute-mapping` (`{ providerId, email?, firstName?,
lastName?, name? }`). The email member decides which account a sign-in is linked
to, so change it with care on a provider that already has users.

### Why a SAML sign-in was refused

When the identity provider's SAML response is not accepted, the sign-in lands on
your `errorCallbackURL` (or the platform's sign-in page) with `error=saml_error`.
For the four common configuration mistakes, `error_description` names the cause
instead of `Invalid SAML response`, and the server writes one `warn` log line
with the `providerId`, `protocol: 'saml'` and the same `cause`. The cause is read
from the response the IdP posted, compared with the provider's configured signing
certificate and IdP entity ID; neither the redirect nor the log line carries any
assertion content, and the answer does not depend on whether the account exists.

| `error_description` | What to check |
| :--- | :--- |
| `saml_idp_status_not_success` | The IdP answered with a failure status instead of an assertion: for example Entra ID's "user is not assigned to the application". Check the user's assignment and the IdP's sign-in log. |
| `saml_response_unsigned` | Neither the response nor its assertion is signed. Turn on response or assertion signing in the IdP application. |
| `saml_signing_certificate_mismatch` | The response is signed with a certificate the provider does not have, usually after the IdP rotated its signing certificate. Update the provider's certificate (several can be configured while both are in use). |
| `saml_issuer_mismatch` | The response is signed with the configured certificate but comes from another IdP entity ID. Check the provider's IdP Entity ID against the IdP's issuer. |
| `Invalid SAML response` | Any other refusal of the response (for example an expired assertion or a broken signature). The server log carries the vendor's line. |

The list is exported as `SSO_SAML_REFUSAL_CAUSES` from `@objectstack/plugin-auth`.

## Per-provider sign-in options

Each registered SSO provider carries these switches. All of them are **off** by
default. The first two apply to OIDC and SAML, the third to OIDC only.

| Option | Column on `sys_sso_provider` | When on |
|---|---|---|
| `allowIdpInitiated` | `allow_idp_initiated` | The provider may start a sign-in from the IdP's own portal, with no request from this platform. |
| `allowJit` | `allow_jit` | Under the `invite_only` audience posture, the provider may create an account for a person who has none and holds no invitation. |
| `skipUserInfo` | `skip_user_info` | The provider's email, name and groups are read from its verified ID token, and its userinfo endpoint is not called. The stored endpoint is kept, and turning the option off uses it again. |

**Changing them.** Use **Setup → SSO Providers → Edit Sign-In Options** on a
provider row. It posts to `POST /api/v1/auth/sso/update-provider` with
`{ providerId, allowIdpInitiated, allowJit, skipUserInfo }`, and
`POST /api/v1/auth/sso/register` takes the same members, as does the Register SSO
Provider bridge (`POST /api/v1/auth/admin/sso/register`) for `skipUserInfo`, which the register form offers as **Read Claims From the ID Token Only**. The people who can change a provider today are the
only ones who can change these options. A value that is not a boolean is refused
**400 `VALIDATION_ERROR`**, and nothing is written. Every option keeps a history,
so every change writes a row to the audit ledger (`sys_audit_log`) and a
field-level line to the record's activity feed, naming the old and the new value.

### IdP-initiated sign-in

With the option off, a sign-in the IdP starts on its own is refused, and nobody
is signed in:

- **SAML.** A Response with no `InResponseTo` redirects to the error page with
  `error=unsolicited_response`.
- **OIDC.** A callback that carries a `code` and no `state` redirects with
  `error=state_not_found`, and so does a request from an IdP app tile that
  carries an `iss` and no `code` (below).

With it on, `@better-auth/sso` accepts that sign-in, and the platform adds no
sign-in mechanism of its own (the app-tile entry below only starts the
vendor's own sign-in). A SAML Response with no `InResponseTo` is validated like
any other and signs the user in. An OIDC callback with no `state` restarts the
flow at the IdP's authorization endpoint with a fresh `state`, and the sign-in
completes from there. A sign-in this platform starts is unchanged either way.

The option belongs to one provider: turning it on for one SAML provider does not
accept unsolicited Responses for another. For OIDC, the column is the only
place it is set. An `allowIdpInitiated` member written into the stored OIDC
configuration is not read, and it is removed on the next write.

#### From an IdP app tile (OIDC third-party-initiated login)

An Okta or Entra ID app tile starts an OIDC sign-in by sending the browser to
the app's *initiate login URI* with an `iss` parameter and no `code` (OIDC Core
1.0 §4, "Initiating Login from a Third Party"). Point that URI at the
provider's callback:

```text
https://<your-host>/api/v1/auth/sso/callback/<providerId>
```

In Okta that is the OIDC app's **Initiate login URI**, with **Login initiated
by** set to *Either Okta or App* and the login flow *Redirect to app to
initiate login (OIDC Compliant)*. A portal that opens a fixed URL (Entra ID's
My Apps opens the app's home page URL) can carry the parameter in that URL:
`…/sso/callback/<providerId>?iss=<the registered issuer, URL-encoded>`.

A request there that carries `iss` and no `code`, `state` or `error` starts
the platform's own sign-in at the IdP, with a fresh `state` (and PKCE when
the provider uses it), as **Sign in with SSO** does, only when all four hold:

1. the provider is a registered OIDC provider;
2. its `allowIdpInitiated` option is on;
3. `iss` is the provider's registered issuer, byte for byte (no case or
   trailing-slash folding);
4. `target_link_uri`, when present, is on this deployment's origin or a
   trusted origin, sent once and not empty. The sign-in then lands there;
   without it, it lands on the deployment's base URL.

A request of this shape that misses any of the four redirects with
`error=state_not_found`, as before, and writes
one `warn` line naming the first condition that failed
(`provider_not_registered`, `provider_not_oidc`, `idp_initiated_off`,
`issuer_mismatch`, `target_link_uri_untrusted`, or `start_refused` when the
start itself is refused, for example by domain verification). The request
signs nobody in and sets no session cookie: the session is created only when
the IdP comes back with a `code` for that `state`, the code exchange succeeds
and the ID token verifies, all by `@better-auth/sso`. `login_hint` is passed
on to the IdP.

### Accounts for people who were not invited

Under the `invite_only` audience posture (the default, see
[Who may sign up](/docs/deployment/self-hosting#who-may-sign-up--and-what-each-posture-tells-a-stranger)),
an SSO sign-in by a person who has no account and no pending invitation is
refused. It redirects to the error page with `error=SELF_REGISTRATION_CLOSED`,
and no user is created. These sign-ins are unchanged:

- a person who already has an account;
- a person with a pending invitation;
- the first human of a deployment that has none yet;
- every sign-in under the `email_domain` or `open` posture.

To let a provider create accounts for everyone its IdP authenticates, as it did
before this rule, turn on `allowJit` for that provider. With
[domain verification](#domain-verification-opt-in) on, a provider still creates
an account only for an email address at a domain it has proven, under every
posture, with or without an invitation and with or without `allowJit`.

## Grant permission sets from IdP groups

An SSO provider, OIDC or SAML, can decide what its users may do from the groups
the identity provider sends at sign-in. It uses the same group mappings
(`sys_idp_group_mapping`) as a
[SCIM connection](/docs/permissions/authentication#scim-connection-credentials):
one mapping model, two sources.

**Where the groups come from.** Set the provider's own claim mapping to fill
`groups`: `mapping.extraFields.groups` names the OIDC claim or the SAML attribute
that carries the user's groups, for example `extraFields: { groups: 'groups' }`
in `oidcConfig.mapping` (or `samlConfig.mapping`) when the provider is registered
through `POST /api/v1/auth/sso/register`. The claim's value may be one string or
a list of strings. A provider whose mapping fills no `groups` signs users in as
before.

For OIDC, the claim is read from the userinfo answer when it carries it, and
otherwise from the ID token the server has already verified. Microsoft Entra ID
puts `groups` only in the ID token, so it needs nothing more.

**Groups overage (Entra ID).** When a user belongs to more groups than fit in a
token, Entra ID sends a reference to Microsoft Graph (`_claim_names`) instead of
the groups. The server does not call Graph. That sign-in grants nothing from
groups, removes the grants the provider made earlier, and logs one `warn` line
per provider naming the fix: in the Entra ID application, emit only the
**groups assigned to the application**, or point the groups claim at the claim that carries
the application's own assignments instead of `groups`.

In **Setup → SSO Providers**, a platform administrator sets the same member
without the API:

- **Register SSO Provider** and **Register SAML Provider** take it as
  **Map: Groups claim** (OIDC) or **Map: Groups attribute** (SAML). Leave it blank
  to map no groups.
- **Show Groups Claim** on a provider shows the claim it reads now, whichever way
  it was set.
- **Edit Groups Claim** changes it, and a blank value removes it. Every other
  member of the provider's mapping is kept as stored. A provider without a
  groups claim signs users in as one registered without it.

**Saving a mapping in Setup.** In **Setup → IdP Group Mappings**, a platform
administrator manages the mappings without the API:

- **Map SSO Group** saves a mapping for an SSO provider: its Provider ID, the
  group as the groups claim sends it (a Group External ID or a Group Display
  Name), and a permission set picked from the security catalog.
- **Map SCIM Group** does the same for a SCIM connection, named by its
  connection ID.
- **Delete Mapping**, on a mapping's row, asks for confirmation and then deletes
  the mapping, as the delete route below does.

A save or a delete the server refuses shows the server's own message in the
dialog, and nothing is stored. There is no generic New or Edit form on the
list: a mapping changes only through these actions or the routes below.

**Saving a mapping through the API.** Operators and scripts save one mapping
per group and permission set through
`POST /api/v1/auth/admin/scim/set-group-mapping`, naming the provider with
`providerId`:

```bash
curl -X POST http://localhost:3000/api/v1/auth/admin/scim/set-group-mapping \
  -H 'Content-Type: application/json' -H "Authorization: Bearer $ADMIN_SESSION" \
  -d '{ "providerId": "okta", "groupDisplayName": "Sales", "permissionSet": "sales_rep" }'
# → { success, data: { mappingId, created, providerId, permissionSet, organizationId, reprojected: false, … } }
```

- Name the source with exactly one of `connectionId` (a SCIM connection) or
  `providerId` (an SSO provider). Name the group with exactly one of
  `groupExternalId` (matched against the group's id, such as an Entra ID group
  object id) or `groupDisplayName` (matched against its exact name).
- The grant's organization is the provider's own organization. An unknown
  provider, or one that belongs to no organization, is refused
  `400 VALIDATION_FAILED` on `providerId`. With SSO off the save is refused `503`.
- Only an ordinary permission set inside that organization can be granted. An
  administrator set, or any set outside the organization boundary, is refused
  `400 VALIDATION_FAILED` on `permissionSet`, and nothing is stored. With no
  security service to judge the boundary, the save is refused `503`.
- `POST /api/v1/auth/admin/scim/delete-group-mapping` with `{ "mappingId": "…" }`
  removes a mapping, and at once the grants of that set its provider made in
  that organization, unless another of the provider's mappings still names the
  set.

**At every sign-in.** The user's grants follow the IdP's groups. A mapped group
grants its set in the provider's organization, and a group the user has left
loses its set at their next sign-in. A sign-in with no groups claim removes the
grants that provider made earlier. The boundary is judged again before every
grant. Only grants the provider itself made are ever removed: a grant made by
hand or through SCIM is never touched. A saved mapping applies at each member's
next sign-in, because a provider sends groups only when someone signs in; use
SCIM when a group change must take effect between sign-ins.

**When applying the mappings fails**, the sign-in still succeeds and the failure
is logged at `error`. The user keeps the grants of their previous sign-in until
the next one applies the mappings again.

## OAuth flow

**Social providers** (Google, GitHub, Microsoft, Apple):
1. User clicks **Continue with Google** (or similar).
2. Client calls `POST /api/v1/auth/sign-in/social` with `{ provider: "google", callbackURL }`.
3. Browser redirects to the provider's consent screen.
4. Provider redirects to `/api/v1/auth/callback/google`.
5. better-auth creates a session and redirects to `callbackURL`.

**OIDC/enterprise providers** (`oidcProviders`): better-auth's generic-OAuth plugin
registers each one as a social provider and adds no endpoints of its own, so the flow uses
the same two routes as above.
1. User clicks **Continue with Okta SSO**.
2. Client calls `POST /api/v1/auth/sign-in/social` with `{ provider: "okta", callbackURL }`,
   where `provider` is the entry's `providerId`.
3. Browser redirects to the provider's authorization endpoint.
4. Provider redirects to `/api/v1/auth/callback/okta`. better-auth exchanges the code, reads
   the user's profile from the ID token or `userInfoUrl`, creates a session and redirects to
   `callbackURL`.

## Linking to an existing account

A social, OIDC or enterprise SSO sign-in may arrive with an email that already belongs to a
local account, one that is not linked to this provider yet. The platform then links the
identity to that account automatically (an *implicit* link) only under these rules:

- **The local account's email must be verified.** If it is not, no link is written and the
  callback redirects with `error=account_not_linked`. The user signs in with their existing
  method and links the provider from account settings, or verifies their email first.
- **The platform identity provider is the exception.** `objectstack-cloud` links to an
  unverified local account, because it creates the environment owner's account itself,
  without a mailbox round-trip.
- **An unlink is honoured.** After a user unlinks a provider, signing in with that provider
  no longer re-links it, for any provider, `objectstack-cloud` included. The user links it
  again explicitly from account settings (`POST /api/v1/auth/link-social` while signed in),
  which also ends the refusal. If the unlink cannot be recorded, the unlink itself fails and
  the provider stays linked.

An explicit link from account settings does not depend on whether the signed-in user's
email is verified. It still requires the provider to vouch for the email (a trusted
provider or an `email_verified` claim) and the email to match the account's.

`account.accountLinking.requireLocalEmailVerified` in the auth plugin config changes the first
rule. Unset (the default) gives the rules above. `true` applies the verified-email
requirement to every provider, `objectstack-cloud` included. `false` turns the requirement
off, which the library warns is an account-takeover risk; the unlink rule still applies.
`account.accountLinking.trustedProviders` relaxes only the provider-side `email_verified`
claim and never the local requirement.

## Notes

- `OS_AUTH_SECRET` must be set to a random string in production (a long random value of 32+ characters is recommended). `AUTH_SECRET` and `BETTER_AUTH_SECRET` are accepted as legacy aliases (read silently, without a deprecation warning). If no secret is set, the auth plugin is skipped in production.
- `OS_AUTH_URL` (or `OS_BASE_URL` as a fallback) must match the domain registered with each provider; it determines the base URL used to build OAuth callback URLs.
- Never commit client secrets to source control — use a secrets manager in production.
- The redirect URI registered with each provider must match exactly: `https://<your-domain>/api/v1/auth/callback/<provider-id>`.
