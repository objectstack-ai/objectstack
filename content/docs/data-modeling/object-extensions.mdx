Every object has exactly **one owning package**. That package defines the table, the
primary key and the core fields, and no second package may claim the same name — the
registry refuses it outright.

An **object extension** is how a package contributes to an object it does not own. It
declares fields, validations and indexes that are merged into the target at boot, and
the result is indistinguishable from fields the owner had authored inline: the same
DDL, the same forms and list views, the same API.

## When to reach for one

| Situation | Do this |
|:---|:---|
| You need extra data on an object another package ships (`sys_user`, a CRM package's `account`) | **Object extension** |
| You need a new business entity of your own | Define your own [object](/docs/data-modeling/objects) |
| Your deployment needs a field on an object an installed package ships | An object extension in that package's paired `.custom` package, the field named `<name>__c` — [below](#customizing-an-installed-packages-object) |
| You need an action, hook, view or page on someone else's object | Declare that artifact at the top level and bind it to the target object — [see below](#what-an-extension-may-not-contribute) |

---

## Declaring one

Extensions are declared on the **package**, in the `objectExtensions` collection — never
on the object schema. There is no `extends:` key on an object and no mixin mechanism.

{/* os:check */}
```typescript
import { defineObjectExtension, Field } from '@objectstack/spec/data';

export const AccountSuccessExtension = defineObjectExtension({
  extend: 'showcase_account',                  // the target object, owned elsewhere
  fields: {
    loyalty_tier: Field.select(['bronze', 'silver', 'gold'], { label: 'Loyalty Tier' }),
    csat_score: Field.number({ label: 'CSAT Score', min: 0, max: 100 }),
  },
  priority: 210,
});
```

```typescript
export default defineStack({
  manifest: { /* … */ },
  objectExtensions: [AccountSuccessExtension],
});
```

The target object is owned by someone else, so `defineStack()` cannot verify it exists —
there is nothing in your package to check the name against. A typo therefore survives
the build and surfaces at boot instead, as a warning that the name has extenders but no
owner; the object is then skipped entirely. If an extension's fields never appear,
check that spelling first.

## What an extension may contribute

| Key | Merge behaviour |
|:---|:---|
| `fields` | **Additive.** Merged into the target's field map. A name the target already has is **replaced**, not merged — never in a `.custom` package, whose added fields all end in `__c`. |
| `fieldPatches` | **Applied, field by field.** Changes the *display* of one of the target's own fields — never one an extension adds — without replacing it — [below](#relabelling-a-vendor-field). |
| `validations` | **Concatenated.** Your rules run alongside the owner's; neither replaces the other. |
| `indexes` | **Concatenated**, same as validations. |
| `label` | Replaces the target's label — with one exception, [below](#extensions-and-tenant-customization). A new `label` with no `pluralLabel` beside it also takes the target's plural off, since that plural names the old label: the object is served as one that declares no plural, and lists title it by its label. Set `pluralLabel` too to serve one. A plural the tenant set stays. |
| `pluralLabel` | Same as `label`. |
| `description` | Same as `label`. |
| `priority` | Not merged — it *orders* the merge. `0`–`999`, default `200`. |

Added fields are ordinary fields, so everything on the
[field reference](/docs/data-modeling/fields) applies: types, validation, `required`,
`group`, formulas, and lookups back to your own objects.

### What an extension may **not** contribute

The merge carries the eight keys above and nothing else. These four are not
"unsupported yet" — there is no slot for them to arrive through, and the schema rejects
each one by name with the alternative to use instead:

| Key you might reach for | Declare this instead |
|:---|:---|
| `actions` | A top-level action with `objectName: '<target>'` in the same stack — it stays in the stack's top-level `actions`, and the engine's schema registry attaches it to the target object wherever the object is served, whichever package registers first; a target no loaded package registers fails the boot |
| `hooks` | A top-level hook in the stack that defines the target object — a hook follows the ownership of its object, and `defineStack()` refuses a top-level hook bound to an object the stack does not define, an extended one included |
| `listViews` | A top-level `view` in the stack that defines the target object — `defineStack()` refuses a top-level `view` whose `list` or `form` data source is an object the stack does not define, an extended one included |
| `fieldGroups` | Add the fields here and declare the groups on the owning object, or assign a Page for the layout |

The same holds for any other key: the extension schema is strict, so an unknown key
fails at authoring time with a prescription rather than being dropped in silence.

## Relabelling a vendor field

Replacing a field through `fields` takes it over whole: its type, its options and its
rules become yours, and the owner's next version no longer reaches it. To change only
what a person *reads* — "Industry" shown as "Sector", a better help text — patch the
field instead:

{/* os:check */}
```typescript
import { defineObjectExtension } from '@objectstack/spec/data';

export const AccountWordingExtension = defineObjectExtension({
  extend: 'crm_account',
  fieldPatches: {
    industry: {
      label: 'Sector',
      inlineHelpText: 'The market the account sells into.',
      options: { technology: { label: 'Tech' } },   // addressed by the stored value
    },
  },
});
```

A patch sets `label`, `description`, `inlineHelpText` and `placeholder` on the field, and
the `label` of an option it addresses by its stored `value` — the display whitelist
(`BASE_FIELD_DISPLAY_WHITELIST`), and nothing else. The field's type, requiredness,
default, formula and which options exist stay the owner's, so the owner's upgrades keep
applying and stored values never change; any other key is refused by name with that
reason.

- **Every read serves it.** The patch is applied in the same merge as the other keys,
  after the additive ones, and the list, the by-name read and the layered view agree.
  Uninstalling the extension serves the owner's text again.
- **It reaches the owner's own fields only.** A field another extension adds — or one
  your own extension adds in `fields` — is not a patch target, whatever the
  priorities: set that field's text where it is declared. The install door and
  `os validate` refuse such a patch, and at boot it is not applied and is named once.
  The platform columns the runtime adds to every object (`created_at` and the rest)
  sit in the owner's stored declaration, so the install door admits a patch of one and
  every read applies it, while `os validate`, which reads the declaration you wrote,
  refuses it.
- **Patch it or take it over, not both.** An extension that names one field in both
  `fields` and `fieldPatches` is refused when it parses: `fields` takes the owner's field
  over whole, so the patch would land on your own replacement and the owner's field would
  reach neither. Keep the patch to change only its display, or keep the `fields` entry
  and set the text there. An option is addressed by its stored `value`, so a key no value
  can be (`Tech Sector`, a label) is refused too.
- **Conflicts resolve like `label`.** Two extensions patching the same key: the higher
  `priority` wins. A tenant who has edited that text keeps their own, [below](#extensions-and-tenant-customization).
- **A patch must name something real.** A key that cannot be a field name (`Industry`,
  `Annual Revenue`, a label) is refused when it parses: `fieldPatches` is keyed by the
  field's name, lowercase snake_case like every key of `fields`. A field the target does
  not declare, or an option value its field does not have, is refused when the package
  installs and by `os validate` when the target is in the same stack. A field whose options come from a
  shared picklist has no option labels of its own to patch. At boot, an unmatched patch
  is not applied and is named once in the log; the boot carries on.
- **Options are the owner's too.** A patch is judged against the options the owner
  declares, everywhere: an option another extension (or your own) adds by replacing the
  field through `fields`, or one a tenant's customization adds, is not one a patch can
  name, so the install door and `os validate` refuse it and at boot it is not applied
  and is named once. If an earlier layer leaves out an option the owner declares, a patch
  of that option is admitted but has nothing to relabel, and the boot names it once.

## Naming the fields you add

Each key of an extension's `fields` is a field name of the target, so it follows the
grammar of the target's own `fields` keys: lowercase snake_case, such as `region_code`
(`region_code__c` in a `.custom` package). A key outside it (`Region Code`,
`region-code`, a label) is refused when the extension parses, at `fields.<key>`.

Field names in an extension are **not** namespace-prefixed by the platform. The
namespace rule (`<namespace>_<name>`) governs the names of objects a package *defines*;
it does not walk `objectExtensions`, and it could not — the target's name belongs to
its owner, not to you.

Nothing therefore stops two packages from contributing the same field name to the same
object: the merge is last-writer-wins by `priority`, so one of the two definitions is
not served. The same goes for an extension whose `fields` redeclares a field the owner
declares. Neither is refused; at boot the registry names each such field once in the log,
with every package that declares it and the one whose definition is served. Name
defensively — prefix added fields with something specific to your package when the
name is at all generic.

**The `__c` suffix is reserved to the customer.** A field named `<name>__c` may be
declared only by a base package's paired `.custom` package, below; in any other package,
on its own objects or in its extensions, it is refused, so a vendor's next version can
never take a customer's field name. The save, publish and restore doors, the install
door, `os validate` and `os build` all refuse it, naming the field.

## Customizing an installed package's object

A customer adds to an object an installed package ships — HotCRM's `crm_account` — from
the base's paired customization package `hotcrm.custom`
([ADR-0146](https://github.com/objectstack-ai/objectstack/blob/main/docs/adr/0146-studio-designs-setup-administers-one-editor-per-item-paired-customize-package.md)
D10). The object is extended, never replaced:

- **Every field the pair adds to a base object ends in `__c`** (`region__c`); an unsuffixed field in a
  `.custom` extension is refused with the suffixed name to use. A field the base
  declares is changed only through `fieldPatches`, [above](#relabelling-a-vendor-field).
- **The extension is an item of the pair.** In code it is an `objectExtensions` entry of
  the `hotcrm.custom` stack; at runtime it is an `object_extension` item saved into the
  pair (`PUT /api/v1/meta/object_extension/crm_account?package=hotcrm.custom`, the body
  `ObjectExtensionSchema` with `extend`), drafted, published and exported like any item.
  Studio's **Add field** on a read-only base object writes exactly that, creating the
  pair on first use.
- **An object takes no `overrides` declaration.** Declaring one on an object is refused,
  naming the extension as the route.

{/* os:check */}
```typescript
import { defineObjectExtension, Field } from '@objectstack/spec/data';

export const AccountRegionExtension = defineObjectExtension({
  extend: 'crm_account',
  fields: { region__c: Field.text({ label: 'Region' }) },
});
```

```typescript
export default defineStack({
  manifest: {
    id: 'hotcrm.custom',                  // the base's id + '.custom'
    namespace: 'crm_custom',              // the base's namespace + '_custom'
    dependencies: { hotcrm: '^3' },       // the base, at its installed major
    /* … */
  },
  objectExtensions: [AccountRegionExtension],
});
```

## Merge order and conflicts

1. The registry picks the **base layer** for the object.
2. Every `extend` contribution is folded onto that base, in ascending `priority` order.
3. Within a fold, the rules in the table above apply: fields and scalars are
   last-writer-wins, validations and indexes accumulate.

So a **higher `priority` is applied later and wins** a conflict. Two extensions with the
same priority are folded in registration order (the one registered last wins), which is not a guarantee to build on —
give competing extensions distinct priorities.

Merging is idempotent: re-registering a package (a metadata rebuild, a dev-server
reload) replaces that package's previous contribution rather than stacking a second copy.

## Extensions and tenant customization

Object contributions come in three kinds, and only the first two can be authored:

| Kind | Who writes it | What it is |
|:---|:---|:---|
| `own` | The owning package | The base definition. Exactly one per object, always. |
| `extend` | Any other package | This page. Folded on top of the base. |
| `overlay` | Nobody, directly | A tenant customization layer, hydrated from stored metadata by the loader. It replaces the base at resolution time and owns nothing. |

The overlay is the seam where a package extension meets a tenant's own edits: when an
overlay exists it *becomes* the base the extensions fold onto, so extension fields
survive a customized object rather than being dropped by it.

<Callout type="warn">
  One deliberate asymmetry, ruled 2026-08-13: an extension's `label`, `pluralLabel` and
  `description` apply only while the base still carries the **packaged owner's** value.
  Once a tenant has renamed the object, the extension's packaged default yields and the
  tenant's name stands. A `fieldPatches` key yields the same way, one field (and option)
  at a time: a field label the tenant edited keeps the tenant's text. Fields, validations and indexes are unaffected — they merge
  either way. There is no escape hatch: a package cannot relabel an object a tenant has
  deliberately renamed.
</Callout>

## Worked example

A customer-success package adds churn tracking to an account object owned by a CRM
package — fields, a rule and an index, without touching the CRM package's source:

{/* os:check */}
```typescript
import { defineObjectExtension, Field } from '@objectstack/spec/data';

export const AccountChurnExtension = defineObjectExtension({
  extend: 'crm_account',
  fields: {
    cs_health_score: Field.number({ label: 'Health Score', min: 0, max: 100 }),
    cs_renewal_date: Field.date({ label: 'Renewal Date' }),
    cs_owner: Field.text({ label: 'Success Manager' }),
  },
  validations: [
    {
      name: 'cs_renewal_date_required_for_at_risk',
      type: 'script',
      severity: 'error',
      message: 'An at-risk account needs a renewal date.',
      // CEL predicate — TRUE means the record is invalid.
      condition: '!isBlank(record.cs_health_score) && record.cs_health_score < 40 && isBlank(record.cs_renewal_date)',
    },
  ],
  indexes: [{ name: 'idx_crm_account_cs_renewal', fields: ['cs_renewal_date'] }],
  priority: 300,
});
```

Every added name carries the `cs_` prefix, so this package cannot collide with the CRM
package's own fields or with another extension's. `priority: 300` puts it after the
default `200`, so it wins against a lower-priority extension of the same object.
