# Maintaining the release history

ObjectStack ships as a **single version-locked train**: every public `@objectstack/*`
and `@object-ui/*` package (the bundled `@objectstack/console` frontend included) is
in the one changesets `fixed` group, so one number describes the whole platform.
That number is the `@objectstack/spec` **major** — the same value as `PROTOCOL_VERSION`.

Because the release history spans ~70 backend packages *and* the frontend under
`ui/`, it is maintained in **three layers**. Each layer has exactly one owner
(generated or curated) — never a hand-maintained aggregate, which is what drifts.

```
write time:   backend or ui/ PR → .changeset/*.md
                       │ pnpm changeset version  (release pipeline)
                       ▼
detail layer: packages/*/CHANGELOG.md,
              ui/**/CHANGELOG.md               ← generated, never hand-edited
                       │ curate per major (backend + frontend)
                       ▼
platform layer: content/docs/releases/vN.mdx   ← the whole-platform big picture
```

## 1. Atomic layer — changesets (written at change time)

Every behaviour-changing PR adds a `.changeset/*.md` describing the change and its
migration **while the context is fresh**. This is the only place humans write
release history, for the backend and the frontend alike. `pnpm changeset version`
fans these out into the per-package changelogs and computes the next platform version.

## 2. Detail layer — per-package `CHANGELOG.md` (generated)

Generated by changesets, with PR links. **Never hand-edit these.** They are the
exhaustive, per-package record for integrators and npm.

### The frontend is a package too

The Console UI lives in this repository under `ui/` (`ui/apps/console`, published as
`@object-ui/console`), and the `@object-ui/*` packages are members of the same
`fixed` group as `@objectstack/*` (#25711, landed by #25745; the earlier objectui pin,
its bump script and its changeset digest were deleted there). A frontend change is
an ordinary PR with an ordinary `.changeset/*.md` at the repository root, and
`changeset version` writes it into the `@object-ui/*` changelogs and the one platform
version like any backend change.

`@objectstack/console` ships that Console's build. `pnpm console:build` runs the root
turbo task `@objectstack/console#build:dist`, which depends on
`@object-ui/console#build` and then runs `packages/console/build-dist.sh`: it copies
`ui/apps/console/dist` into `packages/console/dist`, adds the tracked repo-root
`sdui.manifest.json`, and runs the single-zod canary on the bytes it ships.
`pnpm run release` runs it after `pnpm run build`, so a release ships the Console
from the same commit as the spec it builds against.

> objectui's pending changesets from before the merge still sit under
> `ui/.changeset/`, where the root config does not read them. Moving them into the
> root `.changeset/` before the first joint Version PR is #25831. New frontend
> changesets go in the root `.changeset/`.

#### After a registry change: regenerate the committed manifest (#12924, #17735, #25712, #26051)

The repo-root `sdui.manifest.json` (ADR-0080, the Console's public-tier component
manifest), its provenance record `scripts/sdui-manifest.record.json` and one record
per registry package under `scripts/sdui-manifest.sources/` are generated, and one
command writes them:

```bash
node scripts/gen-sdui-manifest-node.mjs   # no arguments
```

It builds the registry packages under `ui/packages/`, enumerates them from
`ui/apps/console` under plain Node, and serializes them through
`@objectstack/sdui-parser` (it needs `packages/sdui-parser/dist`:
`pnpm --filter @objectstack/sdui-parser build`). Each package record is one line:
a digest of that package's own `src/` and the `sha256` of the artefact it was
verified against. A run rewrites only the records whose line changed, so a PR that
edits one registry package re-records that package alone; the shared record moves
only when the artefact does, and then every package record names the new `sha256`.

A required lint step reads the tracked files on **every PR**:
`node scripts/check-sdui-manifest.mjs` checks the shape, the `sha256` against the
record, and recomputes each package's source digest from the index. A PR that edits
a registry package's source without regenerating goes red there, naming the package,
and the failure text prints the regeneration call. Two PRs that edit different
registry packages touch different record files and do not conflict; two that edit
the same package, or a PR that changes the artefact, still conflict once, and the
later one merges `main` and re-runs the command. ⛔ There is no npm install route to the manifest; that was
deleted by ruling 丙 on #17735.

CI also regenerates the manifest and compares it with the committed bytes (#26137):
the `Build & E2E UI` step "The committed SDUI manifest is the one this tree
generates" runs the same command after the registry is built, on every PR that
touches `ui/`, one of the seven packages objectui consumes (the parser among them)
or the manifest's own files, and again on the merge queue's combined tree. A
difference fails the step with the diff and the command to run. That covers what
the source digests cannot see: an edit to `@objectstack/sdui-parser`, to a package
the registry imports, and two queued PRs whose effect on the manifest only shows
together.

**One producer, one artefact.** `packages/console/build-dist.sh` copies the tracked
`sdui.manifest.json` into `packages/console/dist/`, so the published console carries the
same bytes CI gates.

## 3. Platform layer — `content/docs/releases/vN.mdx` (curated)

The curated, developer-facing "big picture", written for third parties building on
ObjectStack. One page **per major**, leading with breaking changes + migration,
then new capabilities, then notable fixes — and a **Console (Studio)** section
covering the frontend changes bundled in that line. This is the layer the whole
platform version maps to.

**Cadence that scales with rapid iteration:**

- **Major (breaking):** a hand-curated `vN.mdx` is mandatory — migration guidance
  can't be generated.
- **Minor / patch:** do **not** add a page each. Fold them into the current major's
  page under a "What's new in N.x" running section, or leave them to the generated
  per-package changelogs.

### Release notes are grouped by what the reader must do

The GitHub Release body is not the raw CHANGELOG section. `scripts/release-github-releases.mjs`
regroups that section's entries — byte for byte, none dropped — under five headings, in this
order, each read from the declarations the changeset already carries (`Metadata-protocol:`, the
`Clause-②:` arm, the BREAKING banner, the ADR-0087 disposition marker):

| Section | What places an entry there |
|:--|:--|
| 需手动处理 | breaking (`Metadata-protocol: narrowed`, a `(narrowing)` arm, a BREAKING banner or a `!` summary) with no `registered` ADR-0087 conversion |
| 自动迁移 | breaking, with a `registered` conversion that `objectstack migrate meta` applies |
| 新增能力 | `Metadata-protocol: added`, or a non-breaking `Clause-②: yes` widening |
| 语义变化 | `Metadata-protocol: semantic` |
| 其他修复 | everything else — `none`, dependency bumps, and entries written before the declaration existed |

A section with nothing in it is omitted. A curated `vN.mdx` section for the same release uses the
same five headings in the same order, so the hand-written page and the generated body agree on
what a reader must do; the per-package `CHANGELOG.md` keeps changesets' own level grouping.

### Sourcing the Console section for a release

Backend content comes from the spec/package changesets. Frontend content comes from
the same place: the changesets that ui/ PRs added, which `changeset version` writes
into `ui/apps/console/CHANGELOG.md` and the other `@object-ui/*` changelogs for that
version. Read those generated sections (and the release-notes grouping above) to
write the Console section. Framework changesets also carry companion frontend notes
inline, which help where a change spans both scopes.

### No objectui pin, so no pin currency to check

A release ships the Console built from `ui/apps/console` at the commit it releases.
There is no pinned objectui revision to choose, move or keep current: the pin, its
bump PRs, the `Console Pin Freshness` gate (removed earlier by #10134) and `ci.yml`'s
**Console Pin Gate** (retired with the objectui import, #25697) are all history. See
#25711 and #25745 for the cutover. `Type Check UI` and `Build & E2E UI` in `ci.yml`
build the Console from `ui/` in the pull request that changes it.

## Rehearsing the version pass (throwaway clone)

Release-machinery changes are verified by replaying a real version pass in a
**throwaway clone** — never in a working checkout, because the pass consumes
`.changeset/*.md`, rewrites every `packages/*/CHANGELOG.md` and moves the
`package.json` versions. Run the preflight first; it is the difference between a
one-second diagnosis and a hang that looks like progress:

```bash
git clone /home/user/objectstack /tmp/rehearsal && cd /tmp/rehearsal
node scripts/pm/release-rehearsal-clone.mjs --prepare .   # refuse, or repair
pnpm install --frozen-lockfile
pnpm run version                                          # the rehearsal itself
```

### Why the preflight exists (#9555)

A clone taken inside an agent container is **shallow** (it descends from a
shallow checkout, and `.git/shallow` is inherited), and that breaks changesets in
two places at once — same root cause, two entry points, and neither of them says
so:

| symptom | dies in | what you actually see |
|---|---|---|
| `changeset version` never finishes | `getCommitsThatAddFiles`: every changeset resolves to the parentless shallow boundary, so it deepens and retries in a loop with no attempt limit | full CPU, no output, clean `git status` — reads as slow progress; the first attempt was allowed to run 70 minutes |
| `changeset status` cannot answer | `getDivergedCommit` (`git merge-base main HEAD`) — a clone of a container checkout has no local `main` at all | `Failed to find where HEAD diverged from "main"`, and the obvious workaround `--since origin/main` then exits 0 reporting **nothing**, which reads as "no packages to release" |

Diagnosing that cost roughly two and a half hours the first time. The script
carries the whole mechanism, the measurements and the two remedies in its
header — `git fetch --unshallow` (10.2 s, +36 MB here, and it gives changelog
links the *real* add-commits) or an offline two-commit scaffold that leaves the
tree hash byte-identical. Run with no flags it only diagnoses and mutates
nothing; `--prepare` repairs a throwaway clone and refuses to touch anything that
looks like a real checkout. Its `--self-test` runs in `lint.yml` and pins both
directions, so the refusal cannot rot into a guard that fires on everything or on
nothing.

**This is a local-rehearsal trap only.** `release.yml` checks out with
`fetch-depth: 0`, so a real cut has full history and never enters that branch.

## Cutting a release

### Release channels

There are two npm channels, and both are published by `release.yml`:

| dist-tag | Carries | Published by |
|---|---|---|
| `latest` | the stable release (GA) | `release.yml`, outside pre mode — the Version Packages PR flow below |
| `next` | the pre-release (`X.Y.Z-next.N`) | `release.yml` in pre mode: `.changeset/pre.json` says `mode: pre`, `tag: next`, and `changeset publish` publishes under that tag |

There is no `rc` channel. The Cut RC lane that cut `X.Y.Z-rc.N` is retired and its
workflow deleted, and a pre-release cycle enters pre mode with tag `next`, never `rc`.
npm may still carry the `rc` dist-tag from that lane (`17.0.0-rc.6` when the lane was
retired). `scripts/release-dist-tags.mjs` lists `rc` as a retired tag: after
every stable publish it removes that tag (`npm dist-tag rm`) and moves a stale `next`
up to `latest`. Run with no flags, it prints that plan and writes nothing.

`release.yml`'s publish lane is gated by `environment: release`, and it publishes
nothing until a human approves the deployment there. Since ADR-0125 (2026-08-20) the
lane **is** started by the push that lands the Version Packages PR (D1), and is then
held, **whole**, at the environment gate until a required reviewer approves it (D2).
The approval is the release act on that lane, so read ADR-0125 D3 before touching it:
an environment with no required reviewers passes automatically and silently, which on
a push-started lane is not a weakened gate but no gate at all. (`release.yml` also
carries a 6-hourly `schedule`, added by #11233; it reaches only the bookkeeping
`version-pr` job, which has no publish capability by construction.) That is the
2026-08-07 ruling (「版本发布必须是人工的」) re-implemented, not relaxed, and it is not
negotiable in either direction — see `release.yml`'s header for the two releases that
were minted without a human and the lane split that ended it.

### Cutting a GA release — the Version Packages PR flow

Unchanged, and everything that makes a GA release a *judgement* stays here: the
board-clearing pass, the #7275-A cut precondition, and the human review of the
generated changelogs on the PR. A GA release ships the Console built from
`ui/apps/console` at the commit it releases. Merge the `chore: version
packages` PR (#4935); that push is what starts the publish lane, and the run then
waits at `environment: release` for a required reviewer to approve a job named
`Publish <version> to npm (awaiting approval)` — the version read from the commit,
never one you supply (ADR-0125 D1/D2). ⛔ **Actions → Release → Run workflow** is
**not** the GA publish path: since ADR-0125 D4 that dispatch takes no version input at
all, and left unchecked it starts the repair lane for a publish that died partway —
checked, it starts the bookkeeping lane described next.

**First, check #4935 is current** (#11233). It is regenerated on a 6-hourly schedule
rather than on every push, so at cut time it can be up to one refresh window behind
main — i.e. it may not yet carry a changeset that landed in the last few hours.
Compare its head against `main` and, if it is behind, **Actions → Release → Run
workflow** with **`refresh_version_pr` checked**, which runs the bookkeeping lane
only: no audit, no publish, and no deployment parked at the `release` environment.
Wait for the refreshed PR's CI, then merge it. That merge is still the decision to
release, and the `release` environment approval is still the authorisation — neither
is changed by where the refresh came from.

**Then, before approving, check that no nearer `CI` run is still in flight** (#24889).
Open the Release run's **`Full battery green at the version commit`** job, step *Read
the full battery at or before the version commit*. It prints one line per workflow it
reads (`CI`, `Lint & Type Check`), each naming the run it chose and
how many first-parent commits before the version commit that run's head sits. The
gate reads only *completed* runs and never waits (by design: `selectFullBatteryRun`
in `scripts/ci/scheduled-full-run.mjs`), so a run still in progress is invisible to
it. Now open **Actions → CI** on `main`: if a run on the version commit, or on any
commit between it and the one the `CI` line names, is still in progress — a `push`
run (every merge to `main` gets its own since #25373, so the version commit's own push
run is the usual one) or the `schedule` run — **wait for it to complete before
approving**. A run takes about 25–30 minutes (the 20 hourly scheduled runs up to
2026-10-23 00:20Z took 14–39 minutes, median 28.7, 14 of them 25–31). Green: approve. Red: do not approve. It is the reading the gate would
have refused had it been complete, so treat it as that refusal (recovery: the
`full-battery` job's header in `release.yml`). `CI` is the long battery, so it is the
window that matters in practice; an in-flight `Lint & Type Check` or `Spec Shape
Gate` run nearer than its line's run deserves the same wait.

Why: 18.0.0 (version commit `06cab4849a`) was approved on a green gate that had read
scheduled `CI` run 39412016980 on `abd5acdaf7`, **9** first-parent commits back,
because the nearer scheduled run 39419131283 on `81120caac8`, 2 commits back, was
still running. That run concluded **failure** at 12:30Z, minutes after the gate read
(#24879, a stale dogfood fixture), and a later `force: true` dispatch that could see
it was refused. The gate was right about everything it could see; the gap is only
the window in which a nearer run is in flight, and only a human can wait it out.

**The scheduled run is every 4 hours** (`cron: '0 */4 * * *'` in `ci.yml` and
`lint.yml`, hourly until #25771). Two consequences for the reading above. A version
commit can wait **up to 4 hours** for the first *scheduled* full run on or after it;
the gate does not wait for one, because a completed `push` run nearer the version
commit decides first (`FULL_BATTERY_EVENTS` reads both), and no window in the gate
is a clock — it reads the nearest completed run at or before the version commit,
however old. And a `push` run's `Test Core` is affected-only (#16467), so when the
nearest verdict is a push run it is the narrower one. If you want the whole-workspace
verdict on the version commit itself and `main` has not moved past it, run **Actions →
CI → Run workflow** on `main` (and the same for **Lint & Type Check**) and wait for it
rather than for the next scheduled run; once `main` has moved, a dispatched run tests a
later tree and the gate rightly ignores it.

**This is a wait, not a merge freeze.** `main` keeps moving the whole time: the
approval publishes the version commit's tree and nothing that landed after it, so
runs on later commits are not what you are waiting for. The release lanes chose
against coordinated freezes, and a Version Packages PR merged behind `main` is
already handled by `annotate-shipped` (#23818); neither changes.

**After a stable `@objectstack/spec` publish, refresh the retired-after census** (#20390): run `pnpm --filter @objectstack/spec exec tsx scripts/build-retired-after-census.ts` (prefix `NODE_USE_ENV_PROXY=1` behind a proxy) and commit the rewritten `packages/spec/src/conversions/retired-after.census.json` in an ordinary PR — until it lands, the census test holds an unpublished entry's `retiredAfter` only to the range from the last censused release to the label, not to the label exactly.

## Drift guard

`scripts/check-release-notes.mjs` (run in CI as `pnpm check:release-notes`) fails the
build when a released spec major has no `content/docs/releases/v<major>.mdx` wired
into that section's `meta.json`. This is what prevents the "docs stuck at v9 while
the platform shipped v14" gap from recurring. Curated pages started at v9; v10/v11
were never backfilled and are the documented exceptions in the guard.

## The older aggregate files

Root `CHANGELOG.md` and `RELEASE_NOTES.md` were hand-maintained platform aggregates
and drifted. They are retained for their historical entries but are **superseded**
by the three layers above — prefer the per-package changelogs (detail) and the
release pages (narrative) for anything new.
